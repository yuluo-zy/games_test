# 增高操作延迟调查

日期：2026-10-09。范围：定位问题，不修改游戏实现，不提交/推送。

## 结论与边界

按钮处理和领域提交不是此次复测的瓶颈。历史版本的数秒延迟已有明确证据：几何任务与着色器编译共享 AsyncComputeTaskPool，工作任务排队约 3.96 秒，另有未优化的 Bevy dev 依赖放大启动成本。**调查开始时，本地已经包含独立生成线程池及依赖优化配置，本轮没有实施这两项修复。**

当前复测的生成工作在请求提交后不到 1 毫秒开始，不再出现历史的秒级工作线程排队。但不能据此宣布画面已即时响应：主世界换网格、渲染世界准备网格、GPU 队列完成通知是不同的测量点。本轮离屏测试仍观察到渲染侧等待。

没有正在运行的 tiny-garden/showcase 进程可供核对，没有操作系统真实鼠标回放，也没有测量窗口交换链实际呈现时刻。因此**尚未证明用户当前运行窗口中的具体等待时长或唯一根因**，不能擅自认定用户用了旧二进制。

## 当前增高链路实测

使用临时诊断 example，加载生产 GardenPlugin、BuildingKit、PresentationPlugin、OrbitCameraPlugin、DesktopEditorPlugin 和中文工具栏；1440×960 离屏目标、六座单体样例（不含正式启动场景第六座的上层附加体块）。在工具系统之前设置实际「增高」按钮的 Interaction::Pressed，使用原有 UI→命令→领域→后台生成→投影→上传系统，依次执行下列四次修改。

为区分截图读回开销，另一次运行完全不截屏：在渲染世界检查新网格全部进入 RenderAssets<RenderMesh> 后，于 RenderSystems::Render 之后登记 RenderQueue::on_submitted_work_done 通知。

下表来自**不截屏运行**。所有时间从该次按钮事件注入开始计；只有「模型计算」是任务自身耗时，其他列是累计延迟。工作线程开始时间也包含进入艺术编译器之前的布局计算，不能把它叫作精确的纯排队耗时。

| 修改 | 领域提交 | 工作线程进入艺术编译 | 模型计算 | 主世界换网格 | 渲染网格就绪 | GPU 队列完成通知 |
|---|---:|---:|---:|---:|---:|---:|
| 房屋 #2：6→9 米 | 0.56 ms | 0.45 ms | 32.02 ms | 75.72 ms | 93.46 ms | 191.78 ms |
| 房屋 #3：12→15 米 | 0.83 ms | 0.86 ms | 68.22 ms | 164.60 ms | 187.20 ms | 593.01 ms |
| 房屋 #2：9→12 米 | 0.52 ms | 0.48 ms | 44.32 ms | 103.95 ms | 154.70 ms | 932.68 ms |
| 房屋 #2：12→15 米 | 0.36 ms | 0.37 ms | 83.20 ms | 260.80 ms | 410.43 ms | 986.06 ms |

独立的截屏读回运行同样全部成功：领域提交 0.31–0.50 ms，模型计算 27.42–62.36 ms，主世界换网格 68.48–157.35 ms，截图回调 197.74–1151.96 ms。四张读回图像的数据 hash 不同，但 UI 变化也会改变 hash，不能仅凭 hash 证明某个几何像素已更新。

**GPU 队列完成通知不是显示器呈现时刻，也不是纯 GPU 执行耗时**：包含之前提交的队列工作和设备轮询/回调交付等待。渲染网格就绪也不单独证明网格实际被绘制。

## 限制提交频率的对照

保持同一插件/资产/操作，只有诊断程序的离屏更新间隔从 1/60 秒改为 100 毫秒；不是游戏优化或推荐把游戏限制在 10 FPS。

- 模型计算为 26.20 / 55.82 / 35.98 / 38.18 ms。
- 主世界换网格为 201.42 / 201.92 / 202.34 / 202.44 ms，包含更长的更新间隔。
- 渲染网格就绪均约 210.6–210.8 ms。
- GPU 完成通知为 308.96 / 315.86 / 309.97 / 307.76 ms，不再逐次增长；此模式回调本身受约 100 ms 轮询间隔影响。

这支持离屏持续提交时存在渲染侧积压/调度等待，否定「所有剩余延迟都来自慢速模型计算」的解释，但不足以把问题唯一归因于 GPU 性能、阴影或驱动。真实窗口使用默认 Fifo 呈现与交换链节流，离屏纹理目标没有同样的呈现节流；不得把离屏队列积压直接等同于用户窗口故障。

## 源码检查

- `crates/presentation/src/editor.rs`：增高操作生成 Resize 命令，把底层高度增加 3 米。没有人工延时、计时器或网络请求。
- `crates/bevy-adapter/src/lib.rs`：提交后后台重建布局和模型；当前用自有 GenerationPool，默认 2 个线程，max_jobs=4，results_per_frame=2。新结果被收集前保留旧投影。
- `crates/presentation/src/renderer.rs`：每帧最多替换两栋建筑，每栋最多五个材质批次；主线程还执行 CPU 数据复制、generate_tangents、实体替换，渲染世界随后准备 GPU 资源。主世界换网格不是渲染完成信号。
- `Cargo.toml`：当前 dev 工作区代码 opt-level=0，第三方依赖 opt-level=3 / debug=false。工作区的艺术编译确实仍有数十毫秒成本，不能把历史某一次的 1 ms 当作所有房屋的生成预算。
- Bevy 0.19.1 缓存源码：pipeline_cache::create_pipeline_task 使用 AsyncComputeTaskPool；默认 async_compute 分配 25% 逻辑核心、至少 1 至多 4 线程。本机 CPU 为 i7-9700、8 个逻辑处理器。
- 默认 WinitSettings::game 聚焦时持续更新、失焦时约 60 Hz；代码未切换为每 5 秒更新的 desktop_app 模式。
- app.rs 的 900 帧等待仅用于截图预热；正常运行 capture.path=None 时提前返回，不会延迟增高操作。
- ICU4X 中文分词提示仍存在，但本次出现提示时领域提交不到 1 ms、任务及时开始，不能将其认定为秒级等待的已证实根因。

## 后续处理建议（本轮未实施）

1. 在用户实际启动的窗口、相同选中房屋上测量事件、任务、CPU 网格、渲染资源及交换链呈现；先确认运行版本，再区分启动期与稳定运行期。历史验证记录的「约 0.07 秒」是当时建造场景的记录，不是所有增高操作或屏幕显示的统一指标。
2. 给用户立即显示明确的待生成反馈；已有线框拖动预览不覆盖增高按钮的可见连续过渡。
3. 针对当前 CPU 计算/主线程上传做单独测量，评估艺术编译的开发优化级别、后台切线生成及增量更新；不通过盲目加线程扩大竞争。
4. 只有窗口测量证实 GPU/呈现瓶颈后，再调整帧节流、阴影预算和渲染设置，避免把离屏测量特性误修进正式游戏。

临时诊断源码已移除，生产实现保持调查开始时的状态；正常 Cargo 生成的 target 缓存未清理。上述为少量本机样本，不是 p95、release 或跨设备性能承诺。
