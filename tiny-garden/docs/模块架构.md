# Bevy 模块架构与实施路线

> v0.5 · 2026-10-09 · 部件增量、桌面过渡与 M1 体块工具已接入，非完整 P0 完成声明

>

## 1. 设计目标与取舍

上下文自动重构的通用设计见[上下文自动重构系统架构](上下文自动重构系统架构.md)：玩家意图、局部关系、派生结构与运行时展示分层；窗户组合、道路连接和笔画类型变化使用专用解析器，共享事务、依赖失效和增量展示。该设计为下一阶段目标，不表示玩法已实现。

建筑不是一个可拉伸的模型，而是“尺寸、体块关系、层数、样式”的意图集合。改变意图后，规则计算窗格、楼层、屋顶和退台；Bevy 展示结果。

采用轻量 DDD：建筑是聚合根，支撑树、楼层与屋顶意图在聚合内保持一致；编辑用例处理事务与历史；展示与平台在外层。**不引入微服务、通用 Repository 框架、DI 容器、事件总线或完整 Event Sourcing。** 当前内存撤销历史不是持久化事件日志。

拆 crate 的理由是编译器可验证的依赖限制，不是每个功能都要独立包。现阶段六个 crate 各有实质实现；道路、存储、平台暂不创建空壳。新增 presentation 因为 GPU/窗口/UI 依赖与纯核心、调度库有明确边界，渲染由 desktop feature 显式启用。

## 2. 代码依赖方向

2026-10-10 增加共享上传流程与类型规则合同：presentation 的 `upload` 统一管理批次上传、预算、就绪和暂存所有权，各类型实现批次来源及安装策略；generation 的 `structure` 统一解析体块与屋顶，提供按规则类型工作的单快照缓存。预览、正式网格及烟囱定位共用结构规则，未改变 crate 依赖方向。具体设计和测量见[上传与结构规则重构](上传与结构规则重构.md)。

以下箭头表示“依赖”，不是运行时数据流：

```text
garden-bevy ───────→ garden-application ──→ garden-domain ──→ garden-geometry
     └────────────→ garden-generation ───→ garden-domain / garden-geometry
     └────────────→ garden-domain
garden-presentation → garden-bevy / garden-generation / domain（desktop 接入 Bevy 渲染）
```

| 模块 | 所拥有的数据/规则 | 不能承担的责任 |
|---|---|---|
| geometry | Rect、相交/包含、矩形差集 | 不理解房屋、加载资产或启动任务 |
| domain | Building、BlockId、Stories、Roof、Facade；支撑与层数不变量 | 不出现 Bevy Entity、Handle、Resource、输入设备、文件路径 |
| application | Editor、命令、预览、历史、对象版本、任务票据、待生成队列 | 不生产 Mesh，不操作 World，不依赖线程池 |
| generation | 布局、稳定部件身份/输入 key、增量复用、墙面开孔、三屋顶、纯 Mesh 与米制 UV | 不修改领域、不接收输入、不创建实体、不保存文件 |
| bevy-adapter | GardenPlugin、任务执行器、取消、最新目标/反馈、投影、后台切线与帧预算 | 不重复实现领域约束，不把投影当存档 |
| presentation | ArtCatalog、模型清单检查、共享材质、受控网格上传与回收 | 不改领域、不保存权威数据；不把占位物当正式资产 |

领域依赖 geometry 仅用于基础矩形值与运算；geometry 不知道 Building。这是对早期 `scene-core / geometry-core / game-app` 草图的细化：把纯编辑用例和建筑生成从 Bevy 适配中提取出来，保持单向依赖。它不意味着未来每个领域都增加一个 crate。

## 3. 聚合与唯一权威数据

### 3.1 建筑聚合

`BuildingDraft` 是不可信输入 DTO；`Building::try_new` 验证后才得到 `Building`。后者内部字段私有，只提供只读查询与返回新聚合的 `edited`。未来存档只反序列化 DTO，再校验和迁移，不能直接反序列化得到可信聚合。

聚合包含一个建筑全局放置参数和最多 3 个体块：

| 数据 | 含义与边界 |
|---|---|
| BuildingId | 会话中不复用的稳定建筑身份，不是 ECS Entity |
| BlockId | 建筑内部稳定身份；已删除体块的 ID 不能用来创建新体块，撤销可以恢复原身份 |
| Placement | 世界 X/Z 平移、Y 高度、整体 yaw；没有整屋 scale |
| footprint | 所有体块共用建筑局部 X/Z 坐标，单位米；首版体块轴对齐 |
| parent | 直接支撑体块；恰好一个根，不能循环 |
| height | 该体块自身高度，不是世界高度 |
| Stories | Auto 的已选层数或 Locked 的明确层数 |
| roof_intent | 玩家选择的屋顶；不得被堆叠规则永久覆写 |
| facade | 当前石/灰泥/木三类语义，不是材质 Handle |

已实现规则：1–3 个体块；1–4 层；任一支撑链不超过 4 层；子体块四边留 0.15m 支撑余量；兄弟体块不重叠；尺寸与放置必须有限；宽深 1.2–100m，体块总高 ≤16m，单层至少 2.2m。这些数值是工程验证的初始参数，不是最终美术定标。

Auto 按 3m 参考层高选择层数，在半层边界两侧各留 0.2m 迟滞；若下行迟滞边界会低于最小合法层高，则提前减层，避免拖动出现非法高度空档。拖动改变高度时更新已选层数；载入不重新推测层数。Locked 不自动增减，非法层高拒绝提交。

移除体块会一并移除其子树；移除唯一根导致空聚合，拒绝。删除整栋建筑用 `EditCommand::Delete`，不通过制造非法空建筑实现。缩小父层而使子层越界时拒绝，暂不自动挪动子层或偷偷删除子层。

### 3.2 三种数据必须分开

| 类型 | 所有者 | 是否持久化 |
|---|---|---|
| 玩家已提交意图 | Editor 内的 `Arc<Building>` | 未来存储此类参数 |
| 派生目标布局 | generation 输出的 BuildingLayout | 可重建，不作为权威存档 |
| 当前动画姿态、Mesh、材质、Entity | presentation / Bevy | 不保存，不写回领域 |

当前 Editor 的对象集合是内存场景容器，还不是具备名称、主题、种子、文件版本的完整 `SceneDocument`。未来增加这些元数据时保留建筑聚合边界。

## 4. 编辑、预览与撤销

`EditCommand` 有 Create / Edit / Delete / CommitPreview / Undo / Redo；`BuildingEdit` 有 Resize / SetRoof / SetStories / AddBlock / RemoveBlock / Move。公开操作是有意义的用例，而不是任意修改 HashMap 或 ECS 组件。

```text
开始拖动 → begin_preview → 多次 Preview::update → 松开后 CommitPreview
                                  └──────────→ 取消：丢弃 Preview
```

预览持有独立的合法候选建筑，不污染已提交对象、不入历史、不创建持久化变更。非法 update 返回错误且保留最后合法候选；UI 需同时显示无效反馈，不能把错误吞掉。提交检验会话与基准对象版本，若期间有其他编辑则返回 StalePreview，防止覆盖新状态。

一次 CommitPreview 只生成一个历史 Patch。历史只存该建筑 before/after 的 Arc，默认最多 128 步，不克隆整个场景。Undo/Redo 复用快照但**递增对象版本**。新编辑清空 redo；无变化提交不生成历史；失败编辑不修改对象或历史。

当前命令是内存类型，尚不能直接序列化。日志/重放实现时新增版本化记录 DTO，保存解析后的层数与稳定 ID，不保存临时 Preview 或任务句柄。ID 分配器、退出重进后的已用 ID 水位也属于下一阶段存档设计，当前样例手动提供 ID。

## 5. 从参数到建筑变化

`generation::compile(&Building)` 是纯函数，不访问世界或全局资产。

| 参数或关系变化 | 已实现的派生变化 |
|---|---|
| 根体块宽度 3 / 6 / 10m | 正立面每层 1 / 2 / 4 窗格；不无限放大窗户 |
| 高度 3 / 6 / 9 / 12m | Auto 生成 1 / 2 / 3 / 4 层 |
| 增加上层 | 子层基准高度累加祖先体块高度；支撑层实际屋顶变为 Flat |
| 上层比下层小 | 矩形差集得到互不重叠的裸露退台区域 |
| 删除上层 | 下层恢复 roof_intent |
| 整栋平移/旋转 | 保留局部布局与全局放置的分离 |

当前窗格规则为 `(墙长 - 0.8) / 2.1` 向下取整，最少一个，窗宽不超过 0.9m。墙面、楼层、中心向外槽位拥有 PartKey（含建筑、体块、面、层、槽位），尺寸不进入 Key，便于匹配新旧布局。

在布局后增加 `compile_mesh(layout, GeometryProfile)`，输出分材质 MeshData（位置、法线、UV、索引），仍不依赖 Bevy。墙面通过水平带扫描扣除矩形窗孔，生成内外面与洞口侧面；窗内用不透明暗面，框/层间线是程序占位面。双坡/四坡按长边定脊并限制屋顶最大升高；平顶含薄板和低护沿。三角形、法线、索引和有限值都校验。

UV 以建筑局部米数投影，切分后相位不从每块墙重置。2026-10-09 首批四套 Blender 烘焙 BC/N/ORM 已接入，明确 sRGB/线性、Repeat 采样及切线生成。外部 kit 模式通过 `compile_mesh_with_frames(..., false)` 保留结构墙洞/侧壁，不再重复生成占位框或暗面。默认无 kit 模式仍可独立测试。完整檐脊细节、异形窗、手工覆盖、屋顶顶点与装饰 PartKey 仍需实现。

### 5.3 DCC 资产与后台编译

`BuildingKit` 在表现层解析不可变 `kit.json`；编译件与 GLB 从同一份 Blender 网格导出，并有 Khronos 格式与位置/UV 一致性门。GLB 是交换件，运行时不直接加载整栋 SceneRoot，避免固定整屋模型破坏参数化能力。

适配层提供小接口 `ProjectionCompiler`，只接受可变派生布局与 GeometryProfile、返回纯 BuildingMesh。表现层实现接口并以 `Arc<dyn ProjectionCompiler>` 注入 `GardenPlugin`；适配层没有反向依赖 presentation，也没有让领域知道路径/句柄。每个 async job 捕获同一份不可变 kit：先将一个底层窗槽转成门洞，再生成结构，最后按五个材质角色追加窗/门/烟囱。修改后的布局和最终网格一起纳入现有版本票据；上传、拾取、替换/删除回收沿用同一份网格。

本批资产版本在启动时固定，不能热替换 GLB 或将 Worker 指向正在变化的资源。切主题/道路等未来输入仍须显式快照与失效机制。PNG 加载和切线生成留在外层；截图需等待所有真实纹理依赖完成。

## 6. Bevy 的职责与系统顺序

`GardenPlugin` 注册领域协调、顺序与**自有**任务池；`PresentationPlugin` 注册共享材质、受控上传和资源回收。没有为每个数据结构建一个插件；插件是能力的注册入口，不是领域对象。

投影根 Entity 的生命周期归 GardenPlugin 所有；呈现模块可管理其渲染子实体，但不能自行销毁投影根而遗留 ID 映射。跨插件请求删除应提交领域 Delete，资源卸载只清理派生资产。

| 类型 | 当前用途 |
|---|---|
| EditorState Resource | 持有唯一 Editor，只公开只读访问 |
| CommandInbox Resource | 鼠标、触摸、UI 的统一操作入口，有容量限制 |
| EditFeedback Resource | FIFO 操作结果，UI/上层必须消费 |
| Jobs / ProjectionIndex | 外层私有后台任务与 ID→Entity 映射 |
| BuildingProjection Component | 一栋建筑的目标布局及 Arc<BuildingMesh>，非权威数据 |
| ProjectionUpdates Resource | 已接受投影的合并通知，呈现侧不扫描全场景找变更 |
| GenerationFailures Resource | 最多 64 条几何失败诊断，可 drain；失败保留旧有效投影 |
| PipelineStats Resource | 启动/应用/丢弃计数与当前在途任务数 |

```text
未来 Input / UI → Commit → Collect → Dispatch → 未来 Present / Diagnostics
                  │          │          │
              合法提交    票据校验    仅派发最新待生成对象
                         更新 ECS    后台纯函数计算
```

Commit 先于 Collect，确保本帧的新修改使旧结果失效。Collect 先于 Dispatch，释放任务槽后才派发新请求。系统集合显式排序，不依赖注册的偶然先后。

Bevy `Commands` 的实体改动是延迟应用；后续 Present 集合必须排在 Collect 后，使用显式排序边界保证延迟命令已应用，不在任意未排序系统里假定新组件已经存在。

garden-bevy 继续使用 bevy_app / bevy_ecs / bevy_tasks 0.19.1，不引入渲染。garden-presentation 的 desktop 按需引入 Bevy 渲染/窗口/UI，关闭默认 feature 并显式选取，没有 gilrs/手柄依赖。参考 [Bevy 文档](https://docs.rs/bevy/0.19.1/bevy/) 与 [Plugin 指南](https://bevy.org/learn/quick-start/getting-started/plugins/)。未来 GLB 载入、Android 包装和其他特性继续显式选择。

## 7. 异步正确性与背压

JobTicket 包含 session、建筑 ID、object_revision、rules_revision、request_serial。应用结果时必须与 Editor 当前 latest 完全相同，且建筑还存在。

| 情况 | 防护 |
|---|---|
| 连续多次编辑同一建筑 | pending 以建筑 ID 合并，仅保留最新快照 |
| 多栋建筑等待更新 | 以请求先后派发；重写请求移到队尾，低 ID 对象不能持续抢占 |
| 已启动的旧任务较晚返回 | 票据不匹配，丢弃，不写 ECS |
| 撤销恢复旧形状 | 新 object_revision，旧生成结果仍然过期 |
| 建筑参数没变，但外部依赖变了 | invalidate 推进 request_serial；旧结果失效 |
| 切换作品 | session 推进、清空历史/投影/旧任务句柄 |
| 删除建筑 | 清掉 latest/pending 并移除投影 |
| 接入队列已满 | QueueFull 明确返回，上层保留事务等待重试 |
| UI 未消费反馈 | Commit 暂停，保留队列；不能静默丢成功/失败反馈 |

外部依赖目前只是 `invalidate` 扩展入口，**道路关联和依赖快照尚未实现**。后续生成输入要捕获相关道路/覆盖/主题的不可变数据与版本，变更事务通过关系索引同步 invalidation；不能让后台任务读取变化中的全局 Resource。当前 rules_revision 固定为 1，不支持热切主题。

默认：命令队列 128、反馈队列 128、每帧最多执行 16 操作、同时最多 4 任务、每帧最多处理 2 已完成结果、自有生成池 2 线程。过期结果也占本帧完成处理预算。已启动的同对象任务可能暂时并存，但总量不超过 max_jobs。

生成任务必须跑在 `GardenPlugin` 自有的 `TaskPool` 上，**不能**使用 Bevy 的 `AsyncComputeTaskPool`。渲染器在后者上异步创建着色器管线，而该池只分到约 1/4 逻辑核心（本机 8 线程即 2 线程）；共用池会让一次建造请求在管线编译期间排队数秒才轮到执行。`Settings::generation_threads` 配置该池，0 视为非法。

这些是数量预算，不是硬实时毫秒保证。正在执行的 CPU future 无法靠 drop 强行打断；后续复杂网格算法应分阶段并检查取消令牌。ReplaceScene 验证/切换当前是 O(场景对象数)，大场景导入应分批准备后在主线程交换。

## 8. 动画衔接的架构约束

`BuildingProjection::target` 只表示最新目标。后续另建展示状态，存 current、target、velocity/phase、PartKey→可见构件匹配表，不把动画半途中尺寸写回 Building。

当前已提供 `transition::SmoothValue`：按半衰期指数收敛，重定向时保留当前数值，不从旧起点重新播放；不同帧率下相同经过时间得到相同结果。这是可测试的尺寸动画原语，**还没有接到房屋画面**，只保证数值连续，不保证速度连续。美术需要速度连续时可换为解析阻尼弹簧，接口与领域不变。

展示侧下一阶段规则：

- 位置/宽高/色彩按当前值重定向；yaw 使用最短角路径，不直接线性穿过 2π。
- 相同 PartKey 的窗/层间线匹配移动；新增/删除构件做短生长或淡化。
- 屋顶拓扑改变不能硬插值不对应顶点，用参数化结构或短交叉过渡。
- 交互拾取的模型与当前可见主体一致；完整主体优先、细节随后补齐。
- 首次载入不播放全场景建造动画；动画中撤销/再拖动仍从 current 接续。

## 9. 性能策略与边界

已落实：不扫描全世界查建筑变更；权威对象 BTreeMap 定位；单次聚合最多 3 体块；Arc 共享不可变快照；历史有上限；pending 每对象最多一个；在途任务和结果提交有上限；一建筑一粗粒度投影 Entity，窗/砖不是海量 ECS 实体。

当前存储查询/合并 O(log N)，聚合验证的成对比较 O(B²) 但 B≤3；布局生成依赖改动建筑窗格数而非全场景；每帧轮询上限为 max_jobs。历史只保留被改对象，反馈暂时也持有少量快照。建筑和体块 ID 墓碑随该编辑会话的累计身份数量增长，退出/换作品时重建；历史上限不等于全场景内存上限。

构建时运行 `scripts/check-boundaries.ps1`：从 Cargo 的实际解析结果验证 crate 依赖方向、纯核心的所有传递依赖中没有 Bevy、全工程没有 gilrs。新增依赖需先修改架构决策及规则，避免代码扩展悄悄打破边界。

真实 kit 按墙面、屋顶、楼层/立面附件组增量生成；共享 5 种材质，分块按变化上传，每帧默认 512 KiB/8 批次并轮转。删除、替换、暂存和过渡回收有测试；确认 RenderMesh/可见过渡管线就绪，不把 CPU 发布当窗口呈现。ArtCatalog 提供比例/色板，BuildingKit 消费离线模板，renderer 加载纹理，制作顺序见[美术资产制作计划](美术资产制作计划.md)。

后续按测量添加：空间索引、旧/新 AABB 关联失效、分级细节、实例化、GPU 时间/移动设备预算。移动端可能受阴影、透明过渡和填充率限制，不能靠线程池宣称高性能；分块代价见[优化实现与验收](优化实现与验收.md)。

性能验收分别测命令延迟、布局耗时、网格耗时、上传字节、draw call、GPU 时间、峰值内存与 Android 热稳定帧时间。现有微基准分别验证 CPU 布局和 Mesh 编译，不是完整游戏性能。

线程池分工与构建 profile 属于同一条"编辑延迟"边界：生成与渲染器预热必须解耦，依赖也必须在 dev 下优化，否则分类正确的架构仍会表现为"建造后要等很久才更新画面"。实测数据见[模块工程验证记录](验证记录.md)。

## 10. 扩展时如何保持低耦合

本轮回到既有 D2/D3：上层新增/删除/子树移动、所选体块独立宽深/高度、整栋中心旋转、立面选择，以及固定资源池的简化实体预览已接入。领域新增 TranslateBlock/SetFacade，application 管身份和事务，controls 管屏幕投影，preview 只管低成本显示；见[M1 建筑工具推进](M1建筑工具推进.md)。万级世界/LOD/流式加载不加入当前里程碑。

「建筑内增量生成与渐进展示」、即时预览、后台准备和最新目标优先已接入。完整目标共享未变缓冲，表现层仅替换改变的资源；当前一致性组保守地按单栋协调。边界与验收见[增量建筑生成架构](增量建筑生成架构.md)和[优化实现与验收](优化实现与验收.md)。

| 新需求 | 放在哪里 | 保持的边界 |
|---|---|---|
| 道路自动门 | domain 增 Road 意图；application 关系索引；generation 开口规则 | Building 不读取道路 Resource；生成输入捕获依赖 |
| 手工门窗与缩小后休眠 | domain 稳定覆盖；generation 活跃/休眠解析 | 保留玩家意图，不删除不可见覆盖 |
| 多主题/新屋顶 | domain 存语义 StyleId；generation 规则快照；presentation ArtCatalog | 不在领域保存 GLB 路径或材质 Handle |
| 鼠标/触摸 | Bevy input 模块统一 PointerAction/手势所有权 | 不在业务命令内检查鼠标按钮；双指先取消预览 |
| 存档/恢复 | application 用例与窄 SceneStore 端口；外层文件实现 | 完成写入才反馈“已保存”；损坏恢复与版本迁移独立测试 |
| Android 生命周期/相册 | platform 边界，先内聚模块后按依赖拆 crate | 暂停取消预览并请求保存，不直接改 Building |
| 环境动物/养宠 | 后续独立模拟领域，经明确的场景查询/变更接口交互 | 不往建筑聚合塞饥饿值、AI 和交互状态 |
| 进入室内 | 后续独立空间/室内模型及生成策略 | 不改变当前外观聚合权威与编辑入口 |

确实有替换实现需求时才用 trait：比如本地文件/测试内存存储、桌面/Android 平台导出。单实现的 compile 函数、Editor、Building 不为“可能会变”额外套 trait。

后续业务插件按注册能力划分为 PointerInputPlugin、EditorUiPlugin、PresentationPlugin、PersistencePlugin、DiagnosticsPlugin；核心仍是 GardenPlugin。每个插件只接入公开用例/投影/变更接口，不直接获得可随意写的领域内部字段。

## 11. 后续实施顺序与验收门槛

| 顺序 | 实施任务 | 验收后才能进入下一项 |
|---|---|---|
| A1 已完成 | 领域聚合、预览/历史、纯布局、异步投影、测试与微基准 | 无 GPU 可测；核心不依赖 Bevy；局部/过期任务用例通过 |
| A2 基础实现 | 墙体/楼层/三屋顶 Mesh 编译、ArtCatalog、桌面观察窗口 | 几何测试通过；正式美术和全部极端尺寸视觉检查仍待完成；手机验收后移 |
| A3 桌面基础接入 | 统一指针路由、拾取、建造/移动/尺寸、镜头平移、选择/控制点与动画 | 线框/进度、根平滑和整组过渡已接入；真实窗口逐帧验收、完整控制点与触摸仍待完成 |
| A4 | 手工覆盖、道路自动门、墙体切分与空间关系 | 道路进退能生成/恢复门窗；只失效相关对象；旧依赖任务拒绝 |
| A5 | 场景 DTO、ID 分配、版本迁移、原子保存/备份与恢复 | 重开状态相同；失败不丢有效档；生成句柄不进存档 |
| A6 | 原创美术资产接入、桌面预算和窗口/发布回归 | Windows 可分发包、DPI、低画质一致性与资源回收通过；手机渲染/生命周期另开移植关口 |

A2–A6 与上层实现计划逐项关联，不代表完整 P0 功能都在这里列完。室内、宠物和游戏手柄不进入当前实施范围。

新增功能的自检：领域数据是否确需保存？不变量属于哪个聚合？是否只调用公开用例？异步任务是否捕获完整依赖？能否拒绝过期结果？是否能离开 Bevy 测规则？有没有重建整个场景？动画状态是否误写回意图？

## 2026-10-10 · 上下文事务与专用结构

当前已从单栋生成扩展到笔画、墙面开口和地形关系。领域保存 SceneContext 与最小迟滞决策，应用保存一致候选、ChangeSet 和空间读集；纯生成按有向阶段输出 LinearStructure、PathNetwork、FacadeStructure 和地基标高。预览、正式提交及上下文撤销使用同一规则入口，应用层仍不依赖 generation。

后台语义事务接受后才发布意图和决策，旧会话结果被丢弃。共享 GenerationSlots 限制所有类型在途工作，PublicationGroups 协调受影响显示组的 GPU 就绪与共同起点；upload.rs 和 CoherentHandoff 统一上传/回收及交接状态，不解释门窗或道路规则。

路面/地形按固定块缓存；地基键只依赖根轮廓、姿态和局部高度；开口显示槽位按墙面与来源区段映射。派生显示编号由专用来源注册表分配，不能作为权威对象编号。完整接口、操作和性能边界见[上下文系统实现与验收](上下文系统实现与验收.md)。
