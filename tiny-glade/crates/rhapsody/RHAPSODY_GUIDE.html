01 / 基本知识

GPU 怎样把数据变成像素

Buffer 存数据，Texture 存二维或多维数据，Shader 做计算，Pipeline 规定计算与绘制方式。

想象你要画一个三角形。CPU 准备三个顶点的位置，把它们放入 Buffer。GPU 运行顶点 Shader 得到屏幕上的顶点位置，再把三角形覆盖的区域转换为片段。片段 Shader 计算颜色；深度、混合等操作决定最终写进 Texture 的结果。

对象直观含义容易混淆的地方
Buffer一段有长度和用途的数据存储可以存顶点、索引、常量、间接绘制命令；不是只能存顶点
Texture / Image有格式、尺寸、层和 mip 的存储既可保存图片，也可保存深度、法线、计算结果
TextureView选择纹理的一部分并规定观察方式通常不复制像素；会持有底层纹理
Sampler采样规则：过滤、寻址等不是图片数据
Shader在 GPU 上执行的程序compute 不经过三角形光栅化
PipelineShader 加布局、光栅/混合/深度等状态不是渲染图，也不是整个游戏渲染流程
Pass一项有明确资源访问的工作可含多个 draw/dispatch，不能与一次提交等同
Attachment这次绘制要写入或读取的图像附件通常需要指定 load/store、格式和布局

Compute 的模型更直接：启动许多工作组，每个线程读写 Buffer 或 Texture。后处理、数据准备都可以用 compute。dispatch(x,y,z) 是工作组数量，线程总数还取决于 Shader 声明的 local size；需要对边界线程做检查。

教学模型：
像素位置 = VertexShader(顶点, 相机参数)
片段颜色 = FragmentShader(材质, 纹理采样)
输出像素 = Blend(片段颜色, 原有像素)
compute 线程数 = 工作组数量 × 每工作组线程数

Rhapsody 的光栅实现使用动态渲染。RenderPassDesc 等名称仍表达附件合同，不代表运行时还需要创建旧式 VkRenderPass / VkFramebuffer 对象。

02 / 基本知识

理解三条不同的时间线

CPU 写完代码、GPU 执行完命令、窗口显示完图像，是三个不同事件。

CPU 通常先录制一批命令，把它提交给 GPU，然后继续准备下一帧。提交返回，只说明工作被接受。GPU 何时完成，需要信号量或 fence 等完成证明。GPU 渲染完成之后，窗口系统仍可能持有图像用于显示。

这也是为什么“Rust 对象已经 drop”不能直接意味着“现在销毁 GPU 内存”。命令可能还在执行；一帧的 CPU 临时数据、GPU 资源和交换链图像需要各自的释放条件。

操作它能证明它不能证明
结束命令录制命令格式已封闭，可以准备提交GPU 已执行
提交成功该队列接受了工作，发布完成点立即可覆写资源
等待 SyncSet 成功相关 GPU 队列工作已完成显示引擎不再使用交换链图像
呈现完成证明对应呈现使用已结束其他无关 GPU 工作已完成

深入一层：退役队列怎样避免反复扫描

退役条目携带完整 SyncSet，但只排在其中一个待满足队列的有序 FIFO。收集时只弹出时间线已经到达的前缀：如果还有其他队列未完成，就把条目转入那个队列；所有条件满足才销毁。这样无需每帧遍历全部活资源。

模型：
入队：选择一个依赖队列，按该队列 value 插入有序队列
收集：只弹出 value <= completed[q] 的前缀
  若还有未满足队列 → 迁移到那个队列
  否则 → 交给销毁者
每次维护限制 max_scans 与 max_destroys；起始队列轮转。
收集成本随实际触及条目变化；有序插入/迁移不保证 O(1)。

Device::retire 对从未提交的对象直接销毁；已经提交的对象进入维护预算。若队列无法增长，会尝试同步等待依赖再销毁；若无法确认安全完成，则保留/泄漏 native 对象，也不冒险提前销毁。这是极端内存失败的安全取舍。

03 / 总体架构

整个框架是一台怎样的机器

前端描述想做什么，编译器推导执行约束，运行时绑定实际资源，Vulkan 后端把工作交给驱动。

游戏中的建筑、阴影和后处理规则主要由上层提供。Rhapsody 接受这些规则产生的 pass 与资源访问。它不是 Bevy 默认渲染器的一个小插件；实现直接使用 ash/Vulkan，同时复用 bevy_tasks 进行 CPU 任务调度。

device配置与硬件能力 → Device / QueuePlan能力、策略、内存、提交、回收
resource描述/数据 → 资源对象；使用 → 状态句柄、SyncCell、范围状态、托管资源
rg声明与回调 → 计划、帧实例、执行回执编译、绑定、执行与跨帧管理

pipelineShader 与状态 → 管线/编译票据反射、完整键、后台编译、热更新

为什么这样设计

让调用者通过稳定的职责入口找到功能，同时保留已有底层实现。

获得什么

内部细节大多隐藏；可以逐步迁移，避免一次重写整个后端。

付出什么

04 / device

设备、能力和队列怎么选

Device 是整个 GPU 世界的根。创建时协商能力，运行时提供提交、预算和回收，最后按明确顺序拆除。

物理设备表示一块 GPU；逻辑设备表示程序在这块 GPU 上创建的使用环境。同一物理 GPU 上的两个逻辑设备也不能随意交换资源，框架用 DeviceGeneration 区分它们。

组件负责的状态为什么独立
coreash 设备、实例、特性、设备属性、代际所有原生调用的根，最后析构
queues实际队列、时间线、待获取所有权、host flush围绕提交顺序维护
memory分配器、预算、驱逐注册控制显存和 CPU 元数据成本
lifetime退役队列、每次回收预算将最后一次使用与销毁时机分离
caches托管资源表、sampler、setup 池共享服务，避免重复创建

队列类别不是硬件队列的承诺。Graphics、Compute、Transfer 是用途；QueueId 指向实际逻辑队列；queue family 是具有相同能力的一组队列。多个类别可能映射到同一个 QueueId，这时共用锁与时间线。

源码选择策略的摘要：
graphics：要求 graphics + compute；需要窗口时还必须支持 present
compute：优先无 graphics 的 compute 族，再找空闲队列
transfer：优先专用传输族，再考虑其他可用队列
Off → 使用 graphics
Prefer → 尽量独立，失败则映射到 graphics
Require → 必须独立，否则返回 Unsupported

“硬件支持”与“创建设备时已经启用”必须分别检查。后续代码不能只看扩展名字就调用功能。每队列一把锁满足原生队列的外部同步要求；不同队列的提交不必抢同一把全局锁。

析构顺序是设计的一部分：先等待并排空退役对象，再依次释放 caches → lifetime → memory → queues → core。缓存中的弱引用用于避免 Device 与资源互相持有导致循环。

为什么这样设计

把不同生命周期和锁域拆开。

获得什么

队列提交互不全局阻塞；资源释放发生在原生设备销毁之前。

付出什么

组件之间仍须遵守锁顺序；多队列并不保证实际加速。

05 / resource 与 rg::resource

一份资源有三种身份

区分“数据描述”“图内名字”“真实 GPU 对象”，才能看懂资源系统。
层次例子生命周期
描述TextureDesc：尺寸、格式、mip、用途是配置值，不等于已经分配存储
图内身份GraphId + ResourceHandle；TextureId + version只在所属图及版本语义内有意义
托管身份Handle<T>、Managed<T>、ResourceStore槽位加代际，防止删除复用后的旧句柄误指
真实对象Buffer、Texture、TextureView、Sampler持有 native 对象、设备与相关状态
使用与状态SyncCell / RangeStateTable随真实资源记录完成点和范围状态

GraphId 防止拿另一张图里的资源索引来用；version 防止把旧写版本误当作新内容；DeviceGeneration 防止跨逻辑设备误用；代际句柄防止槽位重用的 ABA 问题。这些保护作用在不同维度，不能互相替代。

教学模型：
旧句柄 = { slot: 12, generation: 3 }
删除后复用 = { slot: 12, generation: 4 }
只比 slot → 会认错对象
同时比 generation → 旧句柄失效

图内 T0 --write--> T1 --write--> T2
T0 / T1 / T2 可能使用同一实际纹理；版本不等于复制存储。

Arc 表达 CPU 上谁持有资源；SyncCell 表达 GPU 上谁仍在使用资源。命令录制会保留真实对象与用途，不能仅依赖宿主表里的一个索引继续有效。资源最后一次 CPU 持有消失时，native 对象可能还需要进入延迟销毁。

范围也属于资源合同：Buffer 用字节区间，图像用 aspect × mip × layer 的组合。范围越准确，越容易保留独立工作的并行性；范围描述错误则可能产生真实数据竞争。

为什么这样设计

怎样声明一张渲染图

pass("后处理").read(T).discard_write(U).record(dispatch)

Side Effect即使没有输出消费者也必须保留明确标记的外部可观察操作

图编译器怎样推导执行计划

先找内容从哪里来，再找哪些工作必须留下，最后保证存储访问顺序。

第一类边是内容依赖：B 要读取 A 产生的内容，就有 A → B。对局部写入，编译器会保留多个尚未完全被覆盖的生产者。新写入只移除被它完整覆盖的旧范围，不能粗暴地把“最近一次写”当成整个资源的生产者。

教学模型：
写 A：[0,64)
写 B：[64,128)
读 C：[32,96)
C 需要 A 与 B，因此 A→C，B→C。
区间重叠：a.start < b.end AND b.start < a.end
图像范围还需要分别检查 aspect / mip / layer。

第二步是反向活性分析。以导出资源的生产者和 side_effect pass 为根，沿内容依赖回溯。没有到达的 pass 可以裁剪。随后对保留 pass 生成存储顺序约束：RAW 写后读、WAR 读后写、WAW 写后写；图像即使读后读，只要需要不同布局，也可能要求排序。

屏障如何从声明变成实际操作

先生成符号程序，再结合资源真实状态，得到屏障、等待和状态发布。

假设后处理要读取绘制刚写完的纹理。仅仅按顺序提交，不足以表达全部缓存可见性和布局要求。同步必须说明：之前哪类访问需要完成，之后哪类访问才能继续，旧写入怎样对新读取可见，以及图像布局如何变化。

维度表达什么不应误解为
Pipeline Stage在哪个执行阶段建立依赖整个 GPU 的统一完成时间
Access Mask哪些内存读取/写入需要可见性资源的永久用途标志
Image Layout图像按何种用途组织/访问图像内容已有效
Queue Ownership独占资源范围归哪个族使用跨队列的数据依赖已经消失
SyncPoint跨提交/队列的实际完成依赖任意未来猜测的时间线值

范围状态表可以看成许多不重叠的小单元。新访问先与已有单元求交，将必要部分切开，再按状态转换产生屏障与补丁。Buffer 是一维区间；图像是 aspect、mip、layer 的组合。精确范围避免写 mip0 时无谓阻塞 mip1。

简化状态转换：
old = state(range)
if 新访问写入 or old 有写入 or 布局变化:
    建立必要的执行/内存依赖
if 独占且需要跨族:
    release → 实际信号/等待 → acquire
录制计划中的 patch
提交成功后，用真正 receipt 解析并发布 patch

绑定结果中的依赖既可以引用已有 SyncPoint，也可以引用“本次执行的第 N 批”。后者只在该批成功后解析成真实值，避免伪造尚未发生的提交。普通 raw 访问也使用真实资源的范围状态与成功提交发布机制。

屏障不等于 CPU 等待 GPU。大多数屏障被录入命令，约束 GPU 内部执行；CPU 的 wait 是另一种操作。同步命令也不会替你保活资源对象。
为什么这样设计

静态推导复用，动态状态逐帧绑定，并统一实际状态发布。

获得什么

兼容图内访问、上传和 raw 访问，能处理部分提交后的真实状态。

付出什么

符号状态、绑定状态、native 状态要保持一致；因此需要独立检查器和领域测试。

多队列为什么不只是分配线程

多队列需要同时解决顺序、可见性和队列族所有权。

同一队列内有提交顺序，但仍需要正确屏障。不同实际队列之间，要用时间线信号量表达依赖。不同队列族的独占资源，还需要配对的 release/acquire；两边资源与范围必须一致。

情形需要什么边界
两个类别映射到同一队列同队列顺序与必要屏障不能获得队列级重叠
同族、不同队列时间线等待与可见性不需要跨族所有权转移
跨族 Exclusive等待 + release/acquire没有合法顺序的重叠独占访问可能拒绝
跨族 Concurrent等待及内存依赖免所有权转移；必须列出允许的队列族

等待阶段越保守，潜在重叠越少。StagedDependencies 记录依赖在目标队列首次真正被使用的阶段；无法证明阶段的依赖才扩大到 ALL_COMMANDS。若布局转换也依赖该等待，屏障范围必须正确衔接，不能让转换提前越过信号量。

对 A 的每个使用 pass a、B 的每个使用 pass b，DAG 中都存在 a→…→b。
可别名(A,B) = 兼容 AND (A≺B OR B≺A)

当前计划的成员放在相同 offset=0；不是任意二维装箱。

命令如何并行录制

CPU 并行准备命令，GPU 仍按计划约束执行；两种并行不能混为一谈。

Vulkan 命令池有外部同步要求。当前设计按帧、worker、queue family 管理实际池，每个块持有独占 ChunkLease；Send、非 Sync 的租约让同一池不能被两个线程同时录制。池只有在相关 GPU 使用完成后才能整体 reset。

分块输入是上一帧每个 pass 的 CPU 录制耗时。未知成本用已知均值估计，全未知时用相同权重。每块再加固定开销。算法二分一个预算阈值，按允许切点贪心试切，最终生成连续区间。它是有约束的负载平衡模型，不能把估算结果当成真实下一帧耗时。

目标模型：minimize max(块内估计成本之和 + 每块固定开销)
约束：块数 <= K；不改变 pass 顺序；只在合法边界切分。
实现：二分预算 → 贪心计算块数 → 最后一次生成 ranges。
普通可切边界下约 O(n log S)，S 是成本搜索区间。
禁切边界、成本变化与固定开销会影响实际均衡效果。
实验 04 · 为什么按数量均分不总是好？ 连续分块模型

六个 pass 的估计成本为 [1, 1, 8, 2, 2, 6]，每块固定成本为 1。

按当前源码，冷帧和轻帧也走统一任务池录制路径；PGO 改变分块权重，不负责在串行和并行模式之间自动切换。旧文档中的“轻帧自动串行”不应当作当前行为。

命令不仅保存 native 指令，也保存实际资源 owners 和使用登记。CPU arena 为短期投影与工作数组提供复用存储；帧级各类存储池负责不同租约，不能在仍被回执或在途命令持有时强行重用。

为什么这样设计

把录制块的可变数据与命令池独占权明确交给 worker。

获得什么

可以降低 CPU 录制墙钟时间；结果按输入顺序收集。

付出什么

传统描述符绑定经常围绕每个材质或 draw 准备资源集合。Bindless 把资源放进可索引表，Shader 通过参数中的索引访问。表项本身仍有 native 类型、容量和生存期要求，不是任意指针。

上传、读回和动态常量如何流动

CPU 数据需要经过合适的内存与复制命令；“发起上传”不表示“GPU 已经读到了”。

Staging 是可供 CPU 写入、GPU 复制读取的中转存储。当前传输槽使用独立持久映射分配；当槽仍被 GPU 使用时，CPU 不能覆盖它。读回 ticket 对结果的 CPU 引用也会延长槽位租约，防止数据还没读完就复用。

上传模式允许的优化必须保留的语义
Replacement同 key 的尚未提交替换可被新版本取代保留最新有效替换及容量/epoch 合同
Ordered Delta不可隐式合并或取消每个接受的增量保持 FIFO，跨 epoch 也不能丢
批量纹理上传多个复制工作合并提交和屏障每个纹理范围、像素格式与完成依赖仍正确
读回GPU 复制到 host 可见存储先等实际完成，再按内存一致性合同读取

队列把任务 envelope、payload、历史等容量分别限制。生产帧/服务 owner 调用 flush_uploads 推进任务，不需要为了上传再永久启动一个后台线程。暂存区满时延期或返回相应错误，不能覆盖在飞数据。

若目标内存不是 host-coherent，CPU 写完映射地址后还要 flush；GPU 写给 CPU 的数据可能需要 invalidate。范围须按硬件要求对齐。dynamic_constants.rs 用页/块存放小参数，积累脏范围，在提交前合并 flush。

setup 是较少量初始化/便捷操作的路径，复用 Device 持有的命令池。大批持续变化的数据则适合 TransferManager。两条路径都要接真实完成点和资源状态。跨族上传把 acquire 登记到设备，由后续图批次合并处理；无图时可显式 flush_acquires。

为什么这样设计

用有界槽位和异步票据替代每次上传都全设备等待。

获得什么

复制与渲染可重叠，吞吐更稳定；读回结果寿命可控。

付出什么

要处理容量、对齐、格式和所有权；立即上传接口也可能返回超时或失败。

跨帧历史为什么需要单独管理

上一帧的内存还在，不代表上一帧的内容就是本帧可用的历史。

TemporalTexturePair 通常给出 previous/current 两个角色。算法读取上一帧结果，再写当前结果，下一帧交换角色。Session 管实际对象与 parity，不让调用方只凭帧号奇偶猜测历史状态。

首帧没有历史；尺寸或格式改变后，旧历史也可能不适用。回调通过 history_valid 查询合同，并选择算法自身的首帧路径。命名资源解决“沿用哪个对象”，有效性解决“内容是否真的能读”，二者分开。

事件历史该怎样处理
成功提交且导出合同满足确认历史发布；之后使用仍受 GPU 完成依赖约束
完全未提交的取消放弃本帧，不能伪造新历史
部分批次提交后失败考虑已发生写入，不能简单恢复所有旧内容；失效相应历史
只写了一小部分不能自动宣称整个纹理都已初始化
reset / 尺寸变化明确失效，并按新描述或首帧路径重建使用

成功发布不等于 CPU 同步等 GPU 完成。它表示新的历史有一个合法的生产与依赖链，后续 GPU 使用按该链等待；CPU 若读回仍需等实际完成。

为什么这样设计

用 Session 的事务式发布维护历史角色。

获得什么

失败帧不会悄悄成为“上一帧”；资源重用与内容有效性不混淆。

付出什么

每次重置、部分写、部分提交都需要明确语义；错误历史会跨帧传播。

最后一段：怎样显示到窗口

交换链是窗口系统借给你的图像集合，必须按 acquire、render、present 和完成证明来管理。

为什么主图先提交？acquire 可能因垂直同步或图像不可用而阻塞。主图先进入 GPU，可以在 CPU 等待时继续执行；即使本次没有可呈现图像，上传和历史写入也不会被整帧抛弃。

交换链图像作为普通图资源导入，呈现图可有多个批次和队列。gate_first_use 在首次使用图像之前切批，acquire 的二值信号量等待只挡相关批次。规划器处理最终 PRESENT_SRC_KHR 布局及必要 ownership，最后相关批次发出 rendered 信号。

WSI 的完成域与 GPU 队列时间线不同。严格策略需要 swapchain maintenance1 的能力；兼容策略则依赖明确的再获取或代际等证明，无法证明时保留所有权并返回错误，不能把 queue idle 误当成显示引擎已经释放图像。
