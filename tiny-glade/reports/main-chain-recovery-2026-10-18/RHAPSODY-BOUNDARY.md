# 游戏恢复与 rhapsody 重构的边界

2026-10-18 用户明确要求：以已经重构的 `crates/rhapsody` 为基础增加功能、修复缺陷，不能按原版重新复现 rhapsody。本条已同步项目记忆、旧流程入口和当前协作 agent。

用户进一步澄清：手工算法过于简单时，应依据原版证据直接重构该算法，补齐真实业务复杂度，并同步修复调用方。保留当前工程架构与资源所有权不意味着保留错误或不完整的简化逻辑；仅包装接口不足以完成恢复。

- 原版证据约束游戏侧调用与业务语义：例如先编译后执行、资源读写关系、原 shader 参数、真实实例数、acquire/present 生命周期。
- 这些需求通过现有 CoreRenderBridge、HostTables、FrameDeclarer、VulkanGraphSession、PreparedGraph 和资源所有者实现。它们继续使用当前重构库的 API 与数据流。
- country-core 中的原类型和调用恢复留在游戏侧；macOS 窗口、资源索引与平台差异留在宿主适配层。原内部布局不作为重写图形库的理由。
- 库内只修调用链暴露的实际问题、补现 API 所缺能力。相关改动说明触发场景、现有实现的具体差异、验证范围；不把恢复原内部实现计作目标。

最近的 LUT、indirect、RT、timberframe 与屋顶数据恢复均位于现有模块和宿主接线。原先过度简化的 RT 构建已换成原锁定依赖及实际 CWBVH 流程；矩形/圆形木构架已恢复完整变换与原事件分支；这些改动直接替换现有错误实现。已经验证的加载画面 WSI 测试直接使用当前重构库，连续三帧实际 present 和资源释放通过。完整游戏仍受真实 prefab/图集、全部 SSBO 初始化、完整 snapshot 应用和世界主图消费者等缺口阻碍；有界算法验证和加载画面不能证明整个游戏恢复。
