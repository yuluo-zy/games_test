Recoverable fixed-quality compile OOM — READ-ONLY DESIGN, 2026-10-27

Decision
Current source does not justify a general "catch OOM and render the next frame" change. Session-level compile cancellation is substantially reusable, and a restricted recovery path is feasible, but current declaration-side state/publication semantics block treating every compile OOM as an application-recoverable failure. Do not apply a three-retry policy alone or call the existing next-API-call test actual application recovery. No actual source, Cargo or GPU operation was performed for this investigation.

1. Actual failure/control chain
country-core systems/render_loop/render_frame.rs::render_front_inner:377..381 currently catches physical/world compile OOM and calls recompile_at_reduced_scale:451. That changes scale, clears idle resources, resets temporal tables and waits idle before a second, minimum-extent declaration. The existing fixed-quality proposal correctly removes this fallback, but only returns the typed error.
ProductionRenderer::render_front (production_renderer.rs:1724..1748) runs the front host; country render_front calls abort_frame on Err, production closes frame buffers/display in finish_render and returns the original error. render_back_frame_step:1613..1622 runs normal write_back BEFORE checking front failure, then complete_render_feedback:1552..1575 publishes error and returns RenderStep::Complete.
RenderThread returns the existing RenderSide, drops the read boundary, opens update admission, and wakes the main event loop. Its worker is not poisoned by this ordinary frame error. GameFrameDriver::settle_render:368..388 applies feedback, finishes the pending TemporalCommit using history_submitted, then returns feedback.error. GameFrameDriver::frame:533 and GameLoop::frame handoff:1246 propagate it. LoopLifecycle::dispatch:85 stops on any Err, then event_loop.rs run/run_on_game_thread records first failure, shuts down and exits. Merely returning the original OOM from render_front does NOT implement app recovery.

2. Backend cancellation that can be reused
CoreRenderBridge::compile_built (render_bridge.rs:362) claims the built graph and clears pending_build; VulkanGraphSession::compile_frame (rg/vulkan.rs:2699..2777) executes known rejection/compile through one cleanup path. On failure it abandons named state, clears matching named graph id, aborts the result cache, cancels presentation of this graph, collects frame imports, and returns the original error. compile_built:3077..3161 retires callbacks and marks actual DeviceLost. No prepared session is installed on failure.
CompiledCoreGraph::Drop cancels any unexecuted prepared graph. render_front abort clears main/presentation/acquisition; finish_render clears per-packet buffer resolver and ends the display frame. complete_render_feedback abort_unsubmitted leaves Raster/Terrain producer data eligible for retry; TemporalCommit::finish(history_submitted=false) does not commit camera history. Keep all these paths; do not fake an empty successful frame, initialized graph attachment or successful receipt.
Potential separate waits remain: begin_display_frame's ordinary in-flight throttle and explicit lifecycle/control waits already exist. Recovery must not call wait_idle_and_recycle_resources, clear/reset the whole session or recompile a graph in the same packet.

3. Concrete blocker: effect temporal polarity and declaration progress
render_host.rs:4093..4096 and :4154..4157 return flag=u8::from(named.history_valid): 1 valid history, 0 newly allocated/invalid/unsubmitted. This agrees with country-core render/pass_builder/rg_resources.rs:37..44.
effects_host.rs:205 and :216 map reused=(flag==0), opposite polarity. Thus an invalid history following compile abort can be presented as reused. Painterly's acquire/convolve decision in country painterly.rs:502 uses phase==Pending || !(target.reused && depth.reused), and stroke progress reset uses !strokes.reused. Declaration acquires set phase Ready at :667; progress/timer also advance before submission.
The polarity bug is independently assigned by root for review. Fixing it is necessary, not sufficient: on a warm valid-history frame a failed declaration may already have advanced Painterly CPU progress, normal feedback writes it back, while its GPU generation never executes. The next frame can start generating from the advanced progress and skip the missing stroke interval. Old committed history remaining valid does not establish that the failed frame's increment ran.
render_extract.rs:53..62 currently registers PainterlyState, VermeerState, VermeerDebugControl, ShaderRefactoringState etc. as ordinary declaration writebacks. world_postprocess.rs:221..269 explicitly mutates ShaderRefactoringState at declaration completion and says later failures do not invent rollback. Vermeer uses the same EffectsHost. Therefore "session history correctly abandoned" alone is not an app-content proof.
Smallest follow-on investigation/fix is to classify the GPU-dependent fields/events and use existing RenderExchange.after_submission + invalidate_unsubmitted for those fields/owners, retaining pure CPU control feedback. Do not indiscriminately gate every UI/debug resource or introduce a generic World rollback. Tests must cover a warm effect, an actual failed increment, unchanged game input/ticks, and successful later generation of the missing interval. Cold newly-created history only is insufficient.

3b. Additional concrete blocker: one-shot GPU LUT rendered flag
country-core resources/gpu_lut.rs:100..113 deliberately sets GpuLutDesc.rendered=true immediately after the CPU graph-declaration callback succeeds, before compile or submit, with an explicit comment preserving this even on cancellation/OOM. CoreGraphFrame::with_main_prelude (render_bridge.rs:728,743) calls render_luts before the rest of the world and explicitly does not undo this flag on failure. The normal ExtractSet copies GpuLutTracker as a changed resource (render_bridge.rs:1140); the unsubmitted invalidation list in render_extract.rs does not include it. Thus a failed first LUT-producing frame can leave the render World's one-shot flag true while actual BRDF/water LUT generation never executed. Even if no game-side writeback registers this tracker, an unchanged game source tick can leave the mutated render-side copy present on the next frame. Excluding captures or correcting EffectsHost polarity does not fix this independent case.
A recovery prerequisite must establish actual completion/submission-aware LUT dirty ownership, or explicitly reject recovery of a frame that first declared a LUT. The existing behavior is documented native-timing reconstruction; do not casually reverse it as part of a generic retry loop. Add a cold LUT + later physical compile failure + unchanged source ticks test requiring the real LUT dispatch to occur once on the eventual successful frame, plus warm LUT cancellation proving it does not unnecessarily reinitialize valid content. The former fixed-quality terminal-error proposal intentionally did not prove this.

4. Egui uploads: actual source narrows, but does not remove, the risk
EguiBackend::hand_over:65 moves texture deltas into the packet; an early declaration error can drop an unconsumed local egui backend. Such failures must stay outside initial recovery eligibility unless the remaining delta owner is explicitly retained/rejoined in original order.
For a COMPLETED successful egui.draw followed by physical compile failure, new TextureId publication is not merely a write recorded in the failed main graph:
 egui_gpu.rs:142..191 update_texture -> TextureHost::create_texture (render_host.rs:1984..2018) -> Device::create_texture (raw/device_api.rs:108..129) -> setup::init_texture_data -> SetupPool::record (raw/setup.rs:307..343), which does real command.submit BEFORE the managed/TextureId cache insertion.
Existing-texture partial deltas call TextureHost::upload_regions:1695..1732. UploadBoundary owns the bytes, regions and texture in a queued closure; real Host/DeviceOOM is translated to CAPACITY and the closure is retained at the queue front. It submits independently through with_setup_command, and frame cancellation does not clear the boundary queue. ReadLease Drop/poll advances accepted jobs in order. Hence permanent atlas loss solely because main compile failed is not established for these successful-draw paths.
Still required before recovery approval: real atlas creation and partial update, forced subsequent main compile HostOOM, cancellation, unchanged TextureId on retry, real pixels after deferred upload, no duplicated accepted payload, and budget/cancel recovery. Do not generalize successful-draw evidence to declaration-before-egui, rejected upload, asynchronous terminal upload error or shader-preparation failure.

5. Menu/LUT capture publication remains an app-content risk
screenshot_capture.rs:494..559 publishes Menu/LUT texture slots during declaration. The capture compute copy itself only exists in the main graph. capture_texture:669..751 creates a sampled storage texture, imports it, declares copy and attaches an on_retire flag. TextureHost zero-initializes empty sampled images through independent setup, so this is not proof of an uninitialized native image; the semantic problem is a cleared/stale capture being published as if its graph-produced pixels existed.
retirement_flag/reset_cancelled (:563..610) reset never-submitted requests on later opportunities; explicit cancel_unsubmitted:844 also resets only the matching graph. Both deliberately retain already-published texture owners. They do not restore the old Menu/LUT shared slot. MenuBackgroundResources/LUT shared Arcs may already be visible outside the failed graph. Same-graph publication is needed for later passes, so simply deferring the whole publication may change ordering.
A minimal first recovery scope may explicitly refuse auto-recovery when such new graph-dependent publication occurred. Full capture support needs a specific existing-request pending/commit/cancel protocol, keeping original owner and slot identity and ensuring next-frame consumers cannot accept the failed capture. Do not invent broad generic transaction storage merely to enable retries. Test original/failed/retried slot owner, callback count, actual pixels and App/gallery close/reopen.

6. If prerequisites are proved: smallest recovery policy shape
- Remove only the normal reduced-scale/full-idle fallback using the existing fixed-quality proposal.
- Construct a private, non-Clone rejected-compile proof at the actual build_frame-success -> bridge.compile_built Err boundary. Match the typed OutOfHostMemory/OutOfDeviceMemory variants, not text or every anyhow error whose nested cause happens to contain OOM. The proof must identify the same graph/World owner and require no main submit/history receipt, no handoff/prepared/acquired ownership, successful abort/finish and no lost/poisoned device or secondary cleanup/readback error. Unknown setup/declaration/activation/upload/pipeline/execute/present failures remain terminal initially.
- Carry that proof beside the ORIGINAL error in existing FrameFeedback. Keep RenderStep::Complete; do not keep a failed graph in Pending or redeclare it on the resident worker. Existing feedback/dirty abort/temporal/read boundary completion remains once.
- Acknowledge it before LoopLifecycle.dispatch sees an Err: the current dispatch intentionally stops on all errors and should continue doing so for all unclassified failures. The narrow game-frame settlement path hands a proved rejection to LoopLifecycle's bounded retry owner, preserving the first typed OOM and counting/logging every failed attempt, not reporting successful rendering.
- Reuse LoopLifecycle for small deadline/streak state, not a second renderer/host. Example POLICY ONLY: at most 3 later attempts, deadlines 16/64/250ms after failure observation; after exhaustion preserve first OOM and enter the existing terminal path. These values are not a measured/tuned default and no source has been changed. DeviceLost immediately vetoes recovery; cleanup/auxiliary fatal error cannot be masked by the first OOM.
- Both OS adapters need real timer integration. event_loop.rs:511 AboutToWait currently immediately redraws when renderer is idle; run_on_game_thread:265 uses recv_timeout(0) when not waiting. Gate redraw and use WaitUntil/recv_timeout(min applicable deadline); just returning Ok from settlement creates repeated full graph builds under persistent pressure. Process close/suspend/resize while gated; no sleep loop or busy polling.
- Preserve one-ahead simulation: the next update may already have run before prior feedback is settled. Use existing awaiting_render admission to retain this already-updated CPU frame during retry delay, avoid another Update/egui end/input-edge replay, and extract it only once when allowed. Reset retry owner only after real successful feedback, not after merely queueing an attempt. App switch/shutdown must cancel old-World retry state and never resurrect its packet.
- One existing nonblocking maintenance round (renderer.collect_inner / bridge.collect_completed_frames / device.try_collect_garbage) may advance already-completed ownership between distinct attempts, on the resident owner. It must not replenish an allocation's shared reclaim quota, repeatedly drain until success, clear whole pools, poll/wait indefinitely or allocate a per-draw retry queue. Maintenance failure is terminal/secondary evidence, never converted to another silent retry.

7. Secondary-error hazard to account for
complete_render_feedback currently calls readbacks.finish_frame, which may set feedback.error (gpu_readback.rs:172..174 Device.poll failure), then overwrites feedback.error with the primary returned error at production_renderer.rs:1571. Existing abort_frame also logs cleanup errors rather than returning them. Recovery eligibility must have a separate successful-cleanup/no-auxiliary-error proof; first-error preservation does not mean accepting an OOM retry after DeviceLost was detected during cleanup. Keep the original typed cause, record the secondary failure, and veto continuation. Do not weaken current terminal behavior based on generic OOM classification.

8. Required tests, in order
A. CPU orchestration: Host/DeviceOOM aborts once, original error unchanged, no reduced scale/extent/reset/idle fallback and no second compile in the same call; non-OOM/DeviceLost retains terminal semantics.
B. Real session temporal: named texture/buffer cold reject and warm valid-history reject; on_retire/import/result-cache cleanup once, no new main submit, exact next history-valid and mapping polarity. Real EffectsHost/Painterly/Vermeer consumer checks, not a helper mirroring the intended condition.
C. Actual worker/feedback + lifecycle: one rejected packet completes/admission opens, no false submitted/history flag, dirty producer remains eligible, temporal not committed. Current next simulation update is not run twice. Deadline prevents queued redraws/two event-loop adapters from starting attempts early, finite exhaustion retains first cause, successful receipt resets streak, and App switch/pause/close cancel safely. Inject auxiliary DeviceLost during feedback/cleanup and require terminal stop, not OOM recovery.
D. Egui and capture native regressions described above, plus pending pipeline cancellation/upload cap recovery. A later direct session API call succeeding does not cover these owners.
D2. Cold one-shot GpuLutTracker failure/recovery with unchanged extraction source ticks and real BRDF/water LUT callback/dispatch/pixel evidence. No ordinary effect/capture exclusion may silently leave this case eligible.
E. Actual GameLoop/ProductionRenderThread integration: inject a real compile admission HostOOM (and a controlled DeviceOOM return at the exact real allocator boundary, clearly labeled injection), observe error receipt and Running lifecycle, remove cap, drive actual event timer then ordinary frame path to a real receipt/present with same configured quality and expected pixels. Count actual Update/input consumption, graph builds/submits, GPU history commits, upload/capture callbacks and bounded memory. Add persistent pressure through exhaustion and DeviceLost control. Test image/capture generation must not be replaced with fake success handles.
F. Benchmark rounds retain raw failed/cancelled/insufficient frames and remain invalid on any configured acceptance failure. App availability recovery is not a clean CPU gain or 16ms acceptance; do not delete failed frame tails.

Scope estimate / recommendation
A safe broad implementation is not just the old 2-source fixed-quality patch plus a lifecycle exception. At minimum it coordinates country render-frame, ProductionRenderer, FrameFeedback, GameFrameDriver/LoopLifecycle and both event-loop adapters, with correctness prerequisites for one-shot LUT state, effect progress and capture publication. Some prerequisites can reuse existing submission/abort registration, but mixed CPU/GPU state needs field-level review. Proceed first with the independently-reviewed temporal contract fix and focused progress/publication tests; keep general retry unimplemented until these gates pass. If an initial restricted retry is desired, make exclusions explicit and tested; do not claim all normal-frame OOMs recover.

Final freeze note
Root subsequently reported actual application of only the independent EffectsHost polarity correctness fix and its native lifecycle test, including an additional nonzero-copy pixel assertion. This removes the two-line polarity defect from the current source; it does not resolve warm Ready/progress, one-shot LUT rendered flags or Menu/LUT publication transactions. No Cargo/GPU success is asserted by this design/review. Both the fixed-quality terminal-error proposal and automatic recovery policy remain unapplied. Investigation scope is now frozen; no additional recovery architecture or source patch is proposed here. source-anchors.json separates original audit evidence hashes from current actual-source hashes at this freeze so the historical polarity finding is not misrepresented as unfixed current code.
