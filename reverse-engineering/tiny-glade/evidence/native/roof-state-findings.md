# 原作屋顶状态与更新链：第二轮

输入为 manifest 匹配的 `tiny-glade.rne`，SHA256 `f507a6cea25c5199447b88ba746a5293e64a279f73797ca74c1ce7f4ff2b7d03`。没有执行完整游戏或改动发行目录。五个过程的精确范围来自匹配 PDB，完整指令与限定伪代码见 [roof-state-slice.json](roof-state-slice.json)。

## 已验证的局部状态函数

| 原函数 | VA / 大小 | 已恢复的行为 |
|---|---|---|
| `Roof::new` | `0x1408e31c0` / 89 字节 | 把输入字段复制到输出对象，写入 0..0x54；无循环、无网格生成、无调用 |
| `Roof::ty` | `0x1408e3250` / 16 字节 | 低字节布尔返回：对象 +0x30 的 f32 大于常量 `0x3dcccccd`，或比较无序 |
| `Roof::is_gable` | `0x1408e33b0` / 44 字节 | 上述条件与对象 +0x34 的 f32 等于 1.0 相与 |

`0x3dcccccd` 的 f32 值为 `0.10000000149011612`。`ty` 使用 UCOMISS 后 SETC，无序比较也置 CF。因此 +0x30 为 NaN 时返回 true；`is_gable` 的 CMPNLEPS 同样接受无序比较，但 +0x34 为 NaN 时 CMPEQPS 返回 false。Ghidra 首轮伪代码的普通 `<` 表达式没有保留这一差别。这里恢复的是字节级布尔行为，尚不能把 `ty` 的 0/1 数值正式命名为某两个枚举变体。

构造器写入布局如下，输入序号是观察的 ABI 参数次序，不是原始字段名：

| 输出偏移 | 字节数 | 来源 |
|---|---:|---|
| +0x00 | 8 | 参数 2 的值 |
| +0x08 | 28 | 参数 4 指向的字节 |
| +0x24 | 28 | 参数 3 指向的字节 |
| +0x40 | 12 | 参数 8 指向的字节 |
| +0x4c | 4 | 参数 5 |
| +0x50 | 4 | 参数 6 |
| +0x54 | 1 | 参数 7 |

调用者组件数组观察到步长 0x58；构造器没有写入 +0x55..+0x57。还原接口使用 0x58 字节缓冲，但没有据此宣称完整 Rust 类型及字段名已恢复。

候选代码：[roof_state.rs](../../reconstruction/roof/roof_state.rs)。独立参照为原始机器码的 Unicorn x64 模拟，候选为本机 rustc 编译的 Rust。两个判别函数各覆盖 1348 组输入（边界交叉与固定种子随机位型），包含阈值邻接值、正负零、无穷、quiet/signaling NaN；构造器覆盖 256 组字节输入，并检查未写区域保留及原函数返回输出指针。全部返回布尔值/输出字节一致，报告见 [roof-state-verification.json](roof-state-verification.json)。

限制：只比较输出，没有比较浮点异常状态位；MXCSR 固定 0x1f80；构造器输入使用有效且互不别名的内存；显式字节接口不等同于原 Rust ABI。没有把这些局部测试扩展为整套屋顶行为已验证的结论。

## 空间更新器：可追溯的数据流

`update_roof_spatial`，VA `0x1421a7710`，1459 字节。直接调用映射见 [roof-state-calls.json](roof-state-calls.json)。以下是静态观察，尚未做完整函数的差分验证：

1. 从两段输入范围读取事件，步长 0x10。输入 +8 传给 `PublicWalls::roof_entity`，随后检查实体索引、generation 与组件存在性；无效者跳过。
2. 调用 `PublicWalls::get` 和 `PublicWallState::max_y`，把结果写到 Roof 组件 +0x4c，并写入组件变化标记。
3. 墙样式辅助函数返回值与 Roof +0x54 比较，变化时写入字段，并向另一个 0x20 步长集合追加记录。辅助地址有 `gable_roof_style`、`is_halftimbered` 等符号别名，其真实枚举含义未解决。
4. 读取墙对象 +0x258 的判别值，仅处理小于 2 的值。与 Roof +0x08 开始的块进行判别和浮点字段比较；不同则拷贝该块，并向同一集合追加记录。两个分支比较的字段不完全相同，NaN 会触发不等路径。
5. 调用 `Roof::ty`。返回 0 时调用 `Roof::pivot_3d`，把结果写入另一个 0x30 步长组件的 +0x10..+0x18，并给中间坐标加常量；返回 1 时把这三个坐标写为零。该组件用途与常量语义仍待确认。

因此这里已发现“墙状态 → Roof 状态更新 → 变化记录 → 另一组件位置更新”的原作链路。集合与组件的真实类型、事件消费者、时序和坐标用途尚未验证，不能替换成凭名称推断的网格重建流程。

## 屋底函数：下一层仍需追踪

`generate_roof_stone_floor_and_roof_bottom`，VA `0x1421a6d40`，840 字节。观察到两段 0x20 步长输入记录、实体/组件校验、一个分支的 log2f 调用与数值转换、对 `NaniInstanceMeshDesc::from<MeshAtlasPart>` 的调用，然后向命令缓冲追加 0x38 字节记录。`0x140833250` 同址存在多个符号别名，不能单凭其中的 `LazyTile::from_index` 定义输入含义。

目前这段证据更接近选取/包装 mesh atlas 描述并排入后续操作，而不是在该函数中生成屋顶表面顶点。伪代码未恢复 log2f 的真实浮点输入签名，不能把显示的参数 0 当作实际算法常量。

下一步优先追踪 `roof_visual_shape::get_roof_shape`、`assemble_circular_roof`、`assemble_roof_tiles` 和对应 atlas 数据，以恢复真实曲面、脊线、瓦实例与屋底参数；同时把已观察的字段块联接到 history 参数消费者，确认字段名及变化传播。
