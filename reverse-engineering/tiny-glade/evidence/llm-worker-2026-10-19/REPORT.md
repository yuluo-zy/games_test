# 内网 LLM 长函数测试与委派设置

测试对象是 B 原作 `country_core::systems::history::replay_stairs`，VA `0x140af75b0`。完整反编译去空行后 **703 行**；原 RNE 与 patched EXE 的函数跨度 **2373 字节完全一致**，并鲜读阈值常量 `0x142930d70`。输入、原始行映射、PDB 符号、完整原汇编及每轮失败均保留。没有修改游戏源码、依赖锁或持久数据库，也没有提高游戏还原进度。

结论：该模型能承担有边界的分析初稿与定点复核，但**不能自动接受整份长函数合同**。无思考模式多次犯嵌套条件、字段混淆和方向映射错误；低强度思考明显改善，仍需原指令与主流程裁决。按不同任务/模式逐步定位问题，未把格式检查当语义通过。

## 优化落地

- 保留完整原证据和指纹，只去空白、使用编号原文发送；元数据与源码分开，减少 JSON 转义噪声。
- 固定交付结构：分支矩阵、状态读写、事件公式、缺失查询行为、退出与 drop、未知项和证据行号。
- 区分 scheduling flag 与 payload flag；控制流/浮点有歧义时补定点原汇编。不能把反编译的比较表达式直接认作原指令行为。
- 默认 `chat_template_kwargs={thinking:true,reasoning_effort:25}`；不以关思考换取逻辑正确性。标准厂商开关在本网关实测未生效，有效模板参数依据[本地服务官方说明](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash)。
- 独立、冻结输入的任务默认最多 2 并发；来源/提示词/参数不变的完整结果缓存复用。格式/引用检查与主流程语义验收分开。
- 后续模块合同、相似 producer/consumer 对照、Rust 对原证据核对、字段/事件读写整理优先委派；首次 ABI/别名、复杂算法裁决、跨模块权威状态/生命周期、数据库/源码修改及最终验收保留给主流程。T13 仍排除。

入口：[使用说明](../../scripts/llm-worker/README.md)、[后续提示词](../../scripts/llm-worker/review-production.txt)、[调用器](../../scripts/llm-worker/run.mjs)。已有 v1/v2/v4 提示词保留实验原貌，未用后续改动冒充它们已通过。

## 本轮实际发现

原指令确认事件编号由 **payload bit0** 选择：0 → `0x11 + direction`，1 → `0x12 - direction`。即时/动画标志只控制就绪路径，不控制这个公式。现有 `replay_stairs.rs` 根据 `cmd.instant` 选择音频编号，静态上与该原合同不一致；当前 schema 将 payload 位映射到 `cmd.recreate`。已登记具体表达式与证据，没有在此次工具测试里改游戏代码。

浮点方面，原 `MAXSS` 的第二源操作数是 0.05，NaN 商会被替换为该常量；之后 `UCOMISS/JBE` 的 unordered 进入“加时间后回到扫描”的等待路径，**不是应用状态/事件**。原反编译 C 和初始 checklist 在此不足以证明原语义。本轮据原指令修正，不采纳 worker 的错误执行标签。指令语义参照 [Intel SDM Volume 2B（MAXSS、UCOMISS）](https://cdrdv2-public.intel.com/782151/253667-sdm-vol-2b.pdf)；未观察游戏运行时 MXCSR，特殊未屏蔽异常环境保持未知。

逐项接受/拒绝、原指令地址、初始 checklist 的纠正及候选源码问题见 [owner-adjudication.json](owner-adjudication.json)。这确认辅助工作流和限定静态结论，不宣称完整函数机器码差分、整个历史模块或原游戏交互已验收。
