# rhapsody 与通用游戏引擎的性能比较

日期：2026-10-13。对象为当前恢复中的 rhapsody 候选工程，硬件是 Intel UHD Graphics 630、i7-9700，Windows 10，GPU 驱动 31.0.101.2141。

本机原始测量、逐样本时间和源码 SHA256 保留在 `evidence/hardware-gpu-2026-10-13-165930/`。本次仅提交性能分析文档。既有 lavapipe 数据保留，不能与本机绝对耗时直接比较。

## 可以得出的结论

目前没有 Unity、Unreal 或 Godot 在同机、同工作量下的对照样本，不能给出“rhapsody 比通用引擎慢几倍”的结论。已测结果显示：简单图执行的端到端开销较小；原 blur 在这块 GPU 上成本很高；并行任务粒度和显存分配方式会显著改变框架开销。

引擎比较必须分别观察 CPU 主线程、渲染线程、GPU 和 present 等待，不能把不同口径混在一起。Unity 官方也采用这些独立指标识别瓶颈。[Unity Frame Timing Manager](https://unity.com/blog/engine-platform/detecting-performance-bottlenecks-with-unity-frame-timing-manager)

## 与单帧预算的距离

60 FPS 对应 16.67 ms/帧，30 FPS 对应 33.33 ms/帧。这是目标预算，不是 Unity 或 Unreal 的实测性能。常见帧率目标和 CPU/GPU 瓶颈区分见 [Epic 官方性能分析说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/introduction-to-performance-profiling-and-configuration-in-unreal-engine)。

| 项目 | 本机中位耗时 | 60 FPS 单帧预算占比 | 指标口径 |
|---|---:|---:|---|
| 简单图循环，8 passes | 0.2051 ms | 1.23% | CPU/驱动/等待摊销后的端到端时间 |
| 64 个重回调，原作并行分块策略 | 1.8643 ms | 11.19% | CPU/驱动/端到端时间，含人为 spin |
| blur 256×256 | 4.591 ms | 27.55% | GPU 时间戳区间 |
| blur 512×512 | 19.710 ms | 118.26% | GPU 时间戳区间 |
| blur 1024×1024 | 67.561 ms | 405.37% | GPU 时间戳区间 |

这些行不能相加作为完整帧耗时。简单图仅对 64 字节缓冲做 fill，没有模型、材质、剔除、阴影、UI 或交换链 present。它支持“当前简单图调度开销不大”，不支持“整体引擎已达到成熟引擎水平”。

若每帧都以本次工作方式执行一次 1024×1024 blur，该区间本身已超过 30 FPS 和 60 FPS 预算。但本测试每次重新创建图、资源与管线，TOP_OF_PIPE→BOTTOM_OF_PIPE 时间戳还可能包含前序上传依赖等待；不能把其倒数当作整游戏 FPS，或当作稳定资源复用后的 shader 活跃时间。

## blur 为什么昂贵

原 shader 在本机实际采用 outer=31、inner=9 的循环，加一次中心读取，每个输出像素对应约 280 次逻辑纹理读取。1024×1024 约为 2.94 亿次逻辑读取。逻辑读取数不等于实际显存访问次数，缓存、编译器变换和格式都会影响成本。

仅替换外层引擎没有依据能消除这些工作量。成熟引擎的特效系统会提供降低分辨率、采样质量和迭代次数的配置。例如 Unity URP Bloom 提供 Downscale 和 Max Iterations，但它与本例径向 blur 的效果不同，不能把两者直接当成等价算法比较。[Unity URP Bloom 官方文档](https://docs.unity3d.com/6000.0/Documentation/Manual/urp/post-processing-bloom.html)

本次同 shader 的分辨率扫描结果：1024→512，中位耗时减少约 3.43 倍；1024→256，减少约 14.72 倍。这是减少工作量后的实测收益，不是 rhapsody 相对其他引擎的差距，也不是保持相同画面的无损优化。原 shader 半径以像素计，直接缩放会改变最终显示空间中的模糊尺度。

## 框架层面可量化的优化空间

| 对照 | 本机结果 | 可以推断的范围 |
|---|---|---|
| 重回调原策略并行 vs 串行 | 1.8643 vs 4.1505 ms，约快 2.23 倍 | 64 passes、每 pass 人为 spin 50 µs 的录制负载 |
| 零 spin 原策略并行 vs 串行 | 并行耗时约为串行的 4.09 倍 | 轻回调下任务调度开销明显，需要按负载选择策略 |
| 512 buffers 子分配 vs 专用分配 | 每 buffer 约 5.3 vs 50.8 µs，约快 9.6 倍 | 这一批资源创建/销毁成本，不代表整体帧率提升 |
| 512 buffers 的实际存活内存块 | 子分配 1 块，专用分配 512 块 | 分配粒度；不代表显存容量减少 512 倍 |

帧循环 32 帧提交 32 次、整设备 idle 0 次、逻辑资源登记 2 次，三轮确定性计数器一致。子分配和 balanced 分块为候选扩展，不能把其收益登记为原作机制恢复或原作等价性证明。

## 验证边界

原 blur 全图内部像素正确性测试失败：2116 个内部像素中位相对误差为 0，最大误差 1.1276%，超过 1% 阈值。未放宽原测试。三角函数和采样取整边界差异只是待核实假设。

GPU 时间戳有明显波动，64×64 中位 0.352 ms、P95 7.892 ms；每档只有 15 个采样，nearest-rank P95 即最大值。没有频率、温度、GPU 利用率或其他进程占用数据，无法归因这些尖峰。收尾编译检查曾受并行修改的 shader_compiler 子模块缺失影响；原始失败日志保留。本次数据对应保存的输入哈希，不自动证明后续源码的性能与正确性。

## 如何得到真实的引擎差距

1. 在相同 GPU 上，用直接 Vulkan 与 rhapsody 执行相同 SPIR-V、分辨率、纹理格式和访问顺序；预先创建资源/管线，排除上传和读回，比较稳定 GPU 区间与 CPU 录制/提交开销。
2. 在 Unity 或其他引擎中复现相同工作量，核对实际生成的 shader、格式和同步；固定资源复用、帧在飞数量、VSync 和质量配置。
3. 再比较包含实际模型、剔除、材质、阴影及 present 的同画面场景，分别记录 CPU、GPU、P50/P95 和正确性。

直接 Vulkan 的对照能够识别包装层损耗；同画面场景才能支持完整引擎的性能比较。当前没有这些样本，不能承诺具体差距或优化倍数。
