Tiny Glade 还原工程 · 架构与调用链手册

从 B 版可执行文件与 PDB 骨架出发，重建一个分层的 Rust 游戏工程：country-core 承载游戏规则与渲染声明，systems/* 承载上层系统，tiny-glade 是宿主/二进制，rhapsody 是渲染图后端。

本手册描述的是“还原出来的工程”，不是原作源码。所有百分比是静态审计估计，不是语义等价验收。

这份文档按“为什么 → 是什么 → 怎么跑”组织：

1. 项目脉络

1.1 目标与边界

目标是还原 Tiny Glade B 版的 country-core 业务逻辑，并把它接到一个可运行的宿主上。约束来自项目根目录的 AGENTS.md：

  • 只研究原作发行文件、PDB、游戏自有逻辑；不分析用户的 demo。
  • 优先恢复可编译 Rust 源码与类型/控制流；GPU 真机与场景回放后置。
  • 依赖版本以原作 build-info/Cargo.lock 为准；直接复用 Bevy/glam/serde/fastrand 等通用库，不重写。
  • 引擎是 Bevy 0.16.0 的分叉；只检查必要的分叉差异。

1.2 还原链路

原作 B 版 EXE→ PDB / RNE 机器码→ Ghidra/ReVa 反编译→ skeleton/B 骨架
539 文件 · 函数符号+原地址→ country-core 实现→ systems/* 上层系统→ tiny-glade 宿主→ 可运行程序

骨架（skeleton）只保存 PDB 元数据：每个函数的符号名、首条指令 VA、内联调用关系、依赖来源。它不是源码，但它是“原作到底有哪些函数、在哪个编译单元”的权威索引。还原时以它为对照表，避免凭空发明函数。

1.3 为什么要分成这么多 crate

原作的 PDB 编译单元本来就按模块拆分。还原工程沿用这个边界：

country-core

游戏世界的“规则层”：资源类型、ECS 系统、渲染 pass 声明、存档/历史/输入/UI 的业务逻辑。它不拥有窗口和 GPU 设备。

systems/*

从 core 迁出的、按玩法域拆分的系统 crate：墙、屋顶、装饰、生物、杂项、工具栏、新手引导、水、森林、树、颜色、地形等。

tiny-glade

宿主/二进制：winit 窗口、Vulkan 设备、egui、渲染桥、世界加载、截图、崩溃上报。它把 core 与 systems 装进 App 并驱动主循环。

关键规则：systems/* 依赖 country-core，反向不成立；country-core 依赖 rhapsody 的公开 API，但不拥有设备；tiny-glade 同时依赖两者并负责注入设备与调度。这条方向保证“游戏规则”可以在无 GPU 的环境里编译与测试。

utils（共享工具）

几何、曲线、数值、局部时间、加载 JSON 等。core 与上层 crate 共用，避免重复实现。

asset / asset-pipe / paths

资产 schema、纹理处理/缓存、安装与账号目录策略。启动时决定资源根与用户目录。

tg-*
