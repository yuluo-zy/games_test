## Failure propagation and actual completion gate

v2 retains the original fail-fast load_json_as_mesh/expect behavior. Required missing, invalid or unreadable assets panic before the complete catalog is returned or its insertion command is queued. A partial sequence may already have watched/registered CPU meshes, as in the original; do not claim rollback. That failed World must never become a prepared/presented gameplay World.

For normal splash preparation the existing GameplayPreparation outer catch_unwind around SubApp::update already converts a startup panic into an Err carrying phase/update index and original panic text. It stops reading LoadingGameComplete, performs the existing owned-World save cleanup, and does not warm up or publish. Preserve that boundary.

For skip_splash, GameFrameDriver::frame currently calls App::update without a catch and its Result does not contain startup panics. Minimal necessary host adaptation: wrap that update in catch_unwind(AssertUnwindSafe(...)), convert the real panic payload to an anyhow error with startup/update context, and return before platform output, render host activation, graph submit/present, temporal/fps or success counters. The event-loop Err path already performs ordered shutdown and returns the primary error. This preserves original fail-fast failure as a reportable current-host error; it is not native B panic ABI equivalence. Because the existing leaf unwraps, this path preserves panic/error text, not an original typed std::io::Error object. Typed I/O identity would require a separately authorized fallible leaf API and is not claimed by this design.

The actual completion invariant is canonical ClutterMeshes presence after real Startup deferred application. Add a narrow ensure immediately after each successful gameplay SubApp::update before reading a possible LoadingGameComplete event, and before gameplay render in the synchronous driver. The synchronous check applies to the actual gameplay World selected by its existing world-render mode/canonical Game state, not the loading App. Startup always runs before that App's first Update, so absence is an explicit installation failure, not a reason to spin or send a completion event. No bool, fake event, default catalog, successful missing-asset skip or one-frame counter may stand in for it.

Bevy's real Startup schedule completion applies loader Commands before subsequent state transitions/Update consumers. In the synchronous path validate before GUI output/render. In the worker path inspect actual catalog before checking LoadingGameComplete, and retain the existing real loading event plus graph warm-up gates: catalog presence alone is not readiness to hand off or present. Neither loader success nor catalog presence sends LoadingGameComplete or StartupRevealFinished. Errors continue through existing cleanup even when save cleanup has a secondary failure.
