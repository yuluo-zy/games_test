## GPU publication and upload barriers

VAO creation resolves the same CPU library and uses the actual GraphicsDeviceResource backed by this App's BufferHost. The buffer host calls real `Device::create_buffer` before publishing a slot handle. Device-local initial data takes the existing staging/setup submission path; it is asynchronous, not completed merely because a handle exists. The setup path declares the actual source/destination accesses, records their resource state, submits on the graphics queue, and retains command/staging resources until the real completion point. No extra CPU `DeviceIdle` is justified.

Later typed atlas-slice and instance dirty-range updates call `BufferHost::update_buffer_bytes`. Host-visible buffers take the mapped update path. GPU-only sparse updates use the bounded TransferManager (1 MiB chunks, 4 MiB byte budget, keyed epochs) and `upload_buffer_ranges_wait` for their actual submitted points. The current caller passes `u64::MAX`; there is no finite I/O/GPU deadline guarantee. Cross-family releases may still require the recorded acquire: the graph executor invokes the backend's pending-acquire drain, while frame-token resources remain under graph planning. Unsubmitted drain work is requeued.

For rendering, `RasterHost::refresh_vao_handles` resolves the exact typed VAO and live BufferHost generations, validates index bounds, and retains actual physical buffer Arcs. Indexed Nani packets use the real VAO head and import index/reflected attribute buffers into the frame graph. Core buffer imports likewise resolve managed owners before `import_frame_buffer`. Thus pending initial-upload state and real ownership can flow to graph ordering through existing imports. This is a source barrier chain, not evidence that an actual default world graph submitted or displayed pixels.

The existing loader failure contract remains: synchronous Startup errors/panics become driver Err; preparation errors prevent publish/warmup success; actual catalog presence is an additional gate, not `LoadingGameComplete`. Neither catalog presence, an Atlas CPU entry, a VAO handle nor `GpuWorld` existence is a replacement for original completion and warmup. VAO error retry/log semantics and real render errors must stay observable.

## Live-link reload is a separate current caller gap

Current pure APIs `reload_prefabs`, `reload_mesh_atlases`, `reload_nani`, and `hot_reload_prefabs` exist. The actual installer creates a watcher when `GameConfig.dev.live_link()` is true and registers modification event types, but has no App callers for the four runtime consumers. Changed names/subsets can therefore queue without this business chain being scheduled.

The complete B plugin build at `1408e4b00` always installs the watcher/events and conditionally installs the following **four-member chained Update** tuple when its plugin boolean is true:

1. `reload_prefabs`: mutable watcher/library → `PrefabsModifiedCmd`.
2. `reload_mesh_atlases`: same prefab/Atlas/Mesh libraries plus watcher and prefab events → updated fused meshes plus `MeshAtlasesModifiedCmd`.
3. `reload_nani`: actual GraphicsDeviceResource/Atlas/GpuWorld plus Atlas events → actual atlas-info slice uploads.
4. `hot_reload_prefabs`: actual prefab/Atlas/ActiveSession/GpuWorld/audio/RT World, real instance query, both event readers and Commands → existing-instance business reload.

The build directly stores set tag byte0 and uses the recorded core-systems vtable; its slots include core `systems::impl$0::fmt`, dyn-clone/eq/hash, and an ICF SystemSet slot containing `GameSystemSet`. Update and the exact four types are direct evidence. The exact set-type association is qualified by that vtable/ICF identity rather than treated as a unique non-ICF symbol proof.

The minimal future reload candidate is a same-owner ECS adapter and exact installation for this entire chain, with all actual fourth-member RT/audio/session/query dependencies. Attaching only the first three is not a complete native reload closure. Reload clears/mutates original tables before later fallible operations; do not add an unproven transactional rollback or pretend a partial failed reload is ready. The existing Update44 VAO prefix can consume true fused-mesh modifications. Raw MeshWatch `reload_meshes`/reclaim/geometry remain PostUpdate; moving only the VAO prefix already leaves the documented one-Update boundary for raw PostUpdate changes. This report does not declare full hot-reload phase equivalence.
