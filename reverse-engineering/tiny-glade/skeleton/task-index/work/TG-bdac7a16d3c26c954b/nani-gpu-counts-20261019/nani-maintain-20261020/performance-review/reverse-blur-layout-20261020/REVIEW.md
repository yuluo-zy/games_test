## Conclusion

The new lookup is bounded to the current scheduled pass, uses an immutable compiled plan, performs no driver query, waits or new locking, and retains the exact-view layout/coverage checks needed by the consumer. The reverse-blur views are particularly small: three image bindings per reverse mip, each selecting one color aspect, one mip and one layer. Their residual coverage list can contain at most one range, so this newly added lookup does not spill either SmallVec on that normal reverse-blur path. This statement is limited to the new lookup; the existing host still builds resource/array Vecs and image views, and no zero-allocation claim is made for the full callback or frame.

The general public query is not guaranteed allocation-free: fragmentation can exceed its eight inline residual ranges. There is also repeated scanning for each image view in a pass. Neither has been measured as a bottleneck. No performance blocker is established for the reverse-blur correction, and the strict query should not be weakened or replaced with binding-kind assumptions.

Two concrete duplicate traversals deserve small follow-up only if worth doing in the current integration: default `ShaderBindings::image` now looks up the same ABI slot twice, and individual-mip descriptor padding repeatedly queries the same last mip. Both can be removed locally while retaining all descriptors and checks; neither justifies a new cache framework or a throughput claim.

## Call frequency and work performed

`PassContext::image_layout_for_range` delegates to `image_layout_from_plan` using the current compiled plan and retained/scheduled pass index. Resource descriptor lookup, scheduled-pass lookup and the `program.uses.get(pass.uses)` slice are constant-time. `native_range` normalizes and validates the actual selected view, including the existing depth/stencil policy. Successful normalization has no String formatting allocation. The algorithm then scans only this pass's `RangeUse` slice, filtering by the queried logical resource. It does not scan all frame passes, prior frames or physical resource state.

The normal host callback builds its image resources before `ComputeExecution::execute`. Each graph-managed scalar image occurrence in `access_ranges` makes one query. Each individual-mip ABI array element makes one query, including repeated padding elements. Buffer bindings, external compute bindings and raster bindings do not invoke this new plan query. Rebinding push payloads inside the callback reuses the prepared resources; it does not re-run the selected-view query. Call frequency across a real scene depends on the actual retained compute graph and reflection array counts; no fixed frame-wide count is asserted.

For a reverse pyramid with N declared/retained levels, the three distinct shader bindings cause 3N new exact-view queries during recording. Each reverse pass has only its three image access declarations; native same-top-mip alias combination can reduce the compiled use count. The sampled/storage alias is not two separate descriptor-layout assumptions: both exact bindings query the compiled layout. Forward passes have two image bindings per mip; their lookup cost is separately covered by the same host path. These are source-derived counts, not a rendered-frame measurement.

Let M be the current pass's compiled use count, U the intersecting uses for the requested resource, and F_j the residual range count before processing the j-th intersecting use. One query costs O(M + sum(F_j)) elementary range operations. With Q image descriptor elements, the same pass-use slice is scanned Q times. This is normally a small constant for reverse blur, but image arrays or a pass with many disjoint accesses can amplify it. A compiled-plan cache hit does not eliminate the recording-time queries.

## SmallVec allocation and scale boundary

The two residual vectors use `SmallVec<[NativeRange; 8]>`. Initialization from a one-element slice remains inline in locked smallvec 1.13.2; extension grows only when actual requested length exceeds inline capacity. `difference` returns `SmallVec<[NativeRange; 5]>`: image subtraction produces at most five pieces (other aspects, before/after mip slabs, before/after layer slabs); buffer subtraction at most two. Its own result therefore stays inline. The outer `next` collects results from every residual range, so its total can exceed eight even though each subtraction is inline.

For a single color mip/layer the requested domain contains only one elementary subresource. Subtraction leaves that range intact or removes it. Thus F_j is at most one for normal reverse-blur bindings. In the broader API, image domains are two-dimensional mip/layer rectangles with an aspect mask. Fragments remain disjoint and use endpoints drawn from the requested domain and intersecting cut ranges. A conservative finite bound is the number of aspect-by-mip-by-layer cells induced by those endpoints; there is no eight-fragment guarantee or fixed small use-count cap in this query.

A concrete analytical spill case is a valid one-mip, 19-layer color image. Request all 19 layers and declare disjoint GENERAL-layout layer uses in this order: odd layers 1,3,5,7,9,11,13,15,17, then all even layers 0..18. After the first eight cuts, the residual set has nine disjoint pieces, so the eight-inline outer vector spills. Later even-layer uses complete coverage and the query can succeed. This is a static construction, not an executed test or observed workload. It disproves a blanket zero-allocation claim without implying that reverse blur has this behavior.

A fresh `next` vector is created for each intersecting use. If residuals stay above eight across several steps, several temporary heap lifetimes are possible rather than one retained high-water allocation. The normal-path error behavior remains unchanged; this review does not add arbitrary caps, skip ranges or trade precision for fixed capacity. Existing global plan/resource budgets do not turn an eight-inline local buffer into an eight-fragment semantic limit.

## Specific unnecessary work and narrow options

1. **Default image ABI lookup.** In the candidate host, `image` looks up the ABI slot to choose GENERAL or READ_ONLY, then calls `image_with_layout`, which looks up the same immutable slot again. `BindlessAbi::slot` is a linear `bindings.iter().find`. This adds a second source-level scan to existing raster and external-compute image construction. No heap allocation is introduced by this scan and optimized-code elimination has not been measured. The smallest explicit cleanup is a private constructor taking an already-resolved `BindingKind` plus layout, while both public/default and exact-pass paths retain `validate_image_binding_layout`. The default path can resolve once, select its established layout and call that constructor. The exact-pass path still must query and validate the compiled exact range. No ABI or error-coverage weakening is needed.

2. **Repeated padded mip element.** `individual_mip_views` enumerates A ABI slots but maps all slots after the L actual selected mips to the same final mip. The callback currently repeats `texture.image_view` and `image_for_pass` for these duplicate selections. This source path is reachable from current generate_mips and generate_hzb consumers; the actual A value comes from reflection and was not assumed here. A local loop can resolve and validate each real selected mip once, then clone the last resulting `BindlessResource` into the remaining A-L slots. Every ABI slot must still be written, with the same last actual mip and owner, and each distinct range must still pass exact layout/coverage validation. This reuses a result only within the same immutable PassContext and same view; it is not a cross-frame layout cache or a change to shader work.

3. **General repeated plan scan.** A per-pass resource index or compiled exact-binding projection could reduce Q scans when M/Q are large. That would add plan metadata, cache-key/lifetime obligations and budget work. There is no measured evidence to justify it for these three-range reverse passes. Keep the current small scan for this integration. If later profiling identifies the lookup itself, first distinguish use comparisons, fragment spill and array padding; any acceleration must keep the scheduled index, resource identity, full union coverage and rejection of all intersecting mixed layouts. Do not early-return after the first covering use unless the existing nonoverlap invariant and all conflict checks are explicitly preserved.
