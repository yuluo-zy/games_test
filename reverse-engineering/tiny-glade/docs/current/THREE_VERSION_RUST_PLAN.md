# Tiny Glade 三版本完整逆向与 Rust 项目重建计划

日期：2026-10-10。状态：计划已建立，新增任务尚未执行。

目标：联合三个发行版本的二进制、PDB、资源和构建信息，恢复游戏自有类型、状态、算法、系统调度与渲染接口，交付可构建、可交互、可保存恢复、经过原作对照的完整 Rust 游戏工程。

本计划接替旧单基线计划的后续工作安排。已有成果及验证范围见 PROJECT_PROGRESS.md；三版本静态登记见 [MULTI_BASELINE.md](MULTI_BASELINE.md)。本次编制复用了已有证据，并核对了发行路径及 B/C 锁文件的部分依赖来源，未重新运行完整逆向、游戏或差分测试。

关键限制：

- 三版都含 `tiny_glade.pdb`，各自绑定 GUID/age 与目标二进制；地址采用版本标识加 RVA，不能跨版本复用 VA。
- 三版资源包/着色器组织不同，分别解析、分别记录格式。跨版同名资源仅是候选关系。
- 现有 Bevy 分叉说明与三版材料需要协调：A 的 PDB 登记了 git checkout；B/C 的锁文件分别记录 registry Bevy 0.16.0/0.17.3。registry 来源本身不能排除构建补丁，分叉范围和具体 revision 在 T02 核查后更新，暂不宣称已完全解决。
- C 的锁文件记录 `rhapsody` 来自 `PounceLight/rhapsody2`，另含 `shabriri` git 依赖；可访问性与可复用源码尚未核实，必须独立处理。

## 2. 保留成果与当前缺口

现有 `reconstruction/Cargo.toml` 已是可编译 Rust 工程。屋顶状态、曲面、脊线、矩形/圆形 CPU 铺瓦及部分墙高、屋顶编辑数值规则已有 B 版局部机器码差分证据。第一批任务接续这些模块，避免重新恢复已经验收的相同函数。

当前尚缺权威对象与 ID 的完整映射、历史消费者、创建/更新/删除生命周期、完整墙几何、门窗附着、世界编辑、运行调度与最终渲染集成。屋顶局部完成不能登记为完整屋顶系统。B 的 22 个缺失快照引用先在三版语料中查询，找不到或身份不一致时继续登记缺口，不能用其他文件名相似的快照替代。

当前仍是源码恢复优先。场景回放、GPU 和完整交互验收列入后期必做阶段；它们不是当前类型与 CPU 源码恢复的前置条件。

## 3. 三向差分的操作方法

每个模块按同一个顺序推进：

1. 定位 B 的真实入口、过程范围、类型布局、输入输出与消费者，复用现有函数索引和持久分析数据库。
2. 用 A/C 的源路径、PDB 源文件校验值、符号、调用边和常量寻找候选。路径相同或校验值相同不能单独证明最终机器行为一致。
3. 将候选分类为：行为已证实一致、版本行为变化、迁移/改名/拆分候选、版本独有、映射未确定。优化和单态化导致的一对多映射也要保留。
4. 对影响结果的类型、判别值、状态更新、算法和依赖 API 做差分。恢复作者自有逻辑，依赖实现使用匹配源码和 API。
5. 在原版本输入约束下验证 Rust；再为跨版声明补充对应版本的验证。无法完整模拟的函数登记静态覆盖与未测分支。
6. 写入 Rust 模块、版本映射、证据记录和测试范围，关闭实际链路后再扩展下一模块。

每条恢复记录至少包含：`baseline_id`、二进制 SHA256、PDB GUID/age、RVA/过程范围、源路径、字段/枚举证据、调用关系、Rust 文件和函数、验证输入/结果、排除范围、剩余未知。

证据等级沿用旧计划：E1 文件/符号观察；E2 类型与真实数据流；E3 限定输入的行为差分；E4 运行系统对照。静态反编译不等于执行观察。跨版映射没有证据时标记未知，不把 A/B 的实现直接充当 C 的正确答案。

## 5. Rust 工程如何组织

继续使用现有 `reconstruction/`，按真实接口形成后逐步拆为 workspace。下表是重建工程的模块设计，不代表已恢复作者原 Cargo.toml 或完整原 crate 依赖图。

| crate/模块 | 责任 |
|---|---|
| `tg-model` | 权威对象、ID、枚举、命令与版本语义；不依赖渲染 |
| `tg-history` / `tg-save` | 事务、撤销重做、游戏 schema、快照与迁移 |
| `tg-building` | 墙、屋顶、开口、附着、楼梯及 CPU 几何；承接现有 `roof/` 和 `wall/` |
| `tg-world` / `tg-environment` | 地形、路、水、园景、动物、天气与季节 |
| `tg-assets` | 原作格式、资源 ID、prefab、打包/解包与构建调用 |
| `tg-editor` / `tg-ui` / `tg-audio` | 输入、工具、相机、界面与游戏音频事件 |
| `tg-render` | 实例上传、管线、游戏专属渲染和着色器调用 |
| `tg-mods` | 经确认的 C 版 mod 发现、覆盖、资源联接与热重载 |
| `tiny-glade-rust` | 启动、窗口、系统注册、资源准备与最终可交互应用 |
| 现有 `tg-reconstruction` / 验证工具 | 身份查询、无图形算法调用与差分输出；与运行应用分别构建 |

版本 ABI 适配与正常游戏类型分开：原始内存偏移、未知字节、测试 ABI 留在版本适配/验证层，已确认语义进入正常 Rust 类型。使用 Bevy ECS 管理对象和游戏系统，恢复系统之间的注册和顺序，不复制 Bevy 的查询器/调度器实现。

依赖策略：

- 当前 B 实现继续锁定已经验证的 `glam 0.29.3`、`fastrand 1.8.0`、`half 2.4.1`，迁移前保存报告身份。
- A/B/C 分别保留原锁文件或已确认依赖记录。原作整份锁文件作为证据，不直接覆盖重建工程锁文件。
- C 适配时使用原 C 的版本/revision/features；不能给全部模块直接升级到最新依赖。
- 同一算法依赖不同 glam/RNG/序列化版本时，先在各自基线上验证，再决定版本适配模块或分开的验证 package，避免把不同 Bevy/glam 类型直接连在一起。
- 通用 registry 和可取得的公开 fork 直接复用。自有路径包和私有依赖先确认归属；如果 rhapsody2/shabriri 源码无法取得，单列必要私有接口/逻辑恢复工作，以 A/B 证据辅助，仍需 C 验证。
- 版本/feature/平台/数值实现变化后，旧报告对新构建标记失效并重验；它对原 B 构建的历史验证记录仍保留。

## 7. 验证与完整交付标准

| 验证层 | 方法 | 判定范围 |
|---|---|---|
| 构建 | 固定工具链、`cargo build --locked`，完成拆分后使用 `--workspace`；按目标构建 release 和验证工具 | 只能证明工程及依赖可构建 |
| 类型/静态结构 | PDB、字段读写、判别分支、真实调用/注册与消费者交叉核对 | 证明恢复的数据流与结构边界 |
| 原码算法差分 | 对有界纯函数/解析后的核心运行原指令或受控原函数；输入含正常、边界和错误分支 | 原始布局要求位一致；浮点非位一致项目预先规定误差依据；包含 RNG 最终状态与遍历顺序 |
| 系统状态 | 命令新增、连续修改、取消、删除、撤销、重做、保存/加载、跨对象传播 | 权威状态、ID、派生几何/实例与任务结果逐项核对 |
| 视觉/音频/交互 | 固定相机、环境、种子、画质和操作；核对效果、事件及完整流程 | 静态截图不能代替所有交互场景；不同 GPU 数值差异独立解释 |
| 产品交付 | 干净构建、损坏存档/缺资源/缺 mod、长运行、性能场景与错误恢复 | 必须有可运行应用和完整目标功能验收 |

最终目标是恢复 C 的全部已确认游戏功能与行为；A/B 的关键差异有可追溯解释。验收矩阵覆盖建造编辑、世界编辑、保存恢复、输入/相机/UI、生态/环境/音频、资源/渲染、C 的 mod/后端功能、异常恢复及性能。清单通过包内模块、系统注册、UI入口、数据schema和运行流程交叉建立；每项都有证据、Rust位置、验收结果和剩余未知。

整体完成率等完整功能分母建立后再计算，依赖内部代码、脚本数量、PDB符号数与源路径数不进入完成分母。未知行为、缺样本和未关闭私有依赖不能静默删除。当前所谓源码恢复是行为等价实现，不是已取得作者原始 Rust 文本。

- 独立查询批量执行；本机脚本把大结果存盘，对话只返回版本、位置、结论、缺口和产物路径。CLI 输出按可用的 `--token-limit`、`--token-count`、`--filter-output` 控制。
- 文档用精确 `rg` 和指定区间读取。复用本次已读证据，避免重复倾倒 MASTER_PLAN、进度 JSON 或完整工具目录。大型调查按模块进行，不一次生成十万份伪代码。
- 建议持久产物：`tracking/baselines.json`、`version-map.json`、`module-coverage.json`、`tracking/three-version-plan.json`；新证据按 A/B/C 命名空间保存。既有 B 目录通过显式基线字段归属，不盲目迁移路径。
- 每轮更新实际 Rust 变更、验证范围和残余未知。沿用 `scripts/update-progress.py` 维护旧里程碑之前，先检查它是否支持新增版本字段；计划状态与实现/验收状态分开。

## 9. 需要按证据解决的阻塞
